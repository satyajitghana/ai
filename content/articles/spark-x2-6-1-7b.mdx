Spark-X2.6-1.7B comes with two headline claims: a window of up to a million tokens, and three thinking modes, none, low and high. I wanted to know what each is made of, so I read the repository and then ran the model. Both claims turn out to be plainer than they sound. The window comes from a fixed pattern of three short-window layers to one full layer. The thinking modes are one sentence in the system prompt, plus a prefilled `</think>`.

Labels used throughout: **measured** means I ran it or computed it from a file I downloaded, **reported** means the lab says so and I did not check, **reasoned** means arithmetic or inference from measured pieces.

## What the release is

Spark-X2.6-1.7B is a 1.7B-parameter, text-only, bilingual (English and Chinese) language model published on Hugging Face under the organisation `XHToken`, whose display name is SparkLLM. The model card calls it the second model of the Spark-X2.6 series after the 4B, and says it keeps exactly the architecture of Spark-X2.5-1.7B: the gains are post-training only. The weights are Apache-2.0; I read the `LICENSE` file in the repository and it is the unmodified Apache License 2.0 text, and the card's `license: apache-2.0` agrees with it.

Who is SparkLLM? The post I started from describes it as the lab behind the Spark family, and the name overlaps with iFlytek's Spark (Xunfei Xinghuo) models. I could not confirm a link: the organisation page says only that SparkLLM develops "general-purpose foundation models and professional AI agent products", with two harness products called AStudio and Loomy, and nothing in the model card, the config or the licence names iFlytek. I will not assert the relationship. **Reported** only.

There is no paper. The citation block is a `@misc` entry titled "Spark-X2.6-4B&1.7B: Advancing the Frontier of On-Device Agents for Real-World Tasks". Everything below comes from the repository files, the benchmark SVG on the card, and the runs I did.

The family on the Hub, from the API listing, is: `Spark-X2.6-1.7B`, `-1.7B-Base`, and four derived repositories. Sizes of the files in each, **measured** from the Hub's file listing:

| Repository | Main file | Size |
|---|---|---|

| `-1.7B-FP8` | `F8_E4M3` linears, bf16 embedding | 1.98 GB |
| `-1.7B-INT8` | `I8` linears, bf16 embedding | 1.98 GB |

The INT8 and FP8 headers say what is quantised: 1,438,646,272 parameters are 8-bit, which is exactly the 28 layers of attention and MLP projections (I get the same number below), and the 269,010,944 bf16 parameters are the embedding plus norms and gates. The embedding, 131,072 x 2,048, stays at bf16. That is why an "8-bit" 1.7B model is 1.98 GB and not 1.7 GB, and why `Q4_K_M` is not much smaller than the INT4 safetensors: at this size the vocabulary matrix is 16 percent of the model.

## The layout, read from the config

The repository uses custom code (`modeling_spark.py`, 483 lines, `trust_remote_code=True`), so there is no native transformers class. I read the file instead of running it, and re-implemented the forward pass from it (the next section says how). The numbers in `config.json`:

| Field | Value |
|---|---|
| layers / hidden / MLP | 28 / 2,048 / 6,656 (GELU, gated) |
| query heads / KV heads / head dim | 8 / 2 / 256 |
| vocabulary | 131,072, tied input and output embedding |
| `layer_types` | three `sliding_attention`, one `full_attention`, repeated seven times |
| `sliding_window` | 512 |
| `max_position_embeddings` | 1,048,576 |
| RoPE, full layers | `rope_theta` 5,000,000, `partial_rotary_factor` 0.25 |
| RoPE, window layers | `rope_theta` 10,000, `partial_rotary_factor` 1.0 |
| attention output | headwise sigmoid gate, `g_proj` of shape 8 x 2,048 |

Parameter count, **measured** from the safetensors shape tables, matches the header's 1,707,657,216: per layer 3,072 x 2,048 (fused QKV) + 2,048 x 2,048 (output) + 3 x 6,656 x 2,048 (MLP) = 51,380,224; times 28 is 1,438,646,272; plus the 268,435,456-parameter embedding, 28 x 16,384 gate weights, and 116,736 norm weights.

Three details I checked against the code. There is no QK-norm. Grouped-query attention is aggressive: 8 query heads share 2 key-value heads, so keys and values are 512 wide each (2 x 256) against a 2,048-wide query. And each head's attention output is multiplied by `sigmoid(g_proj(x))`, one scalar per head per token, before the output projection. The gate is computed in float32 and cast back.

## How the 1M window is reached

There is no RoPE scaling entry, no YaRN, no linear or sparse attention in the code. The long window comes from two choices that are visible in `config.json` and `modeling_spark.py`.

1. **Three of four layers cannot see far.** A `sliding_attention` layer masks keys more than 512 positions back. These 21 layers carry local syntax and nothing else, and their cache is bounded.
2. **The fourth layer is full attention with a slow, partial rotary.** Its `rope_theta` is 5,000,000 against 10,000 in the window layers, and only a quarter of the 256 head dimensions are rotated (64 of them). The other 192 dimensions carry no position at all. My reading, **reasoned** and not tested by ablation: the unrotated dimensions let a full layer match on content at any distance, and the slow frequencies keep the rotated ones from wrapping inside the window.

The consequence for memory is arithmetic, **reasoned** from the config. Per token, one full layer stores K and V for 2 heads x 256 dims in 16-bit: 2 x 2 x 256 x 2 bytes = 2,048 bytes. Seven full layers: 14,336 bytes per token. At 1,048,576 tokens that is 14.0 GiB. If all 28 layers were full, 56.0 GiB. The 21 window layers add a constant 21 x 511 x 2,048 bytes, about 21 MiB.

<KvBudget />

The decode cost is where this stops looking free. With a 1M context, each new token must read the whole 14 GiB of full-layer cache, against 3.2 GiB of weights, and attention does 7 layers x 8 heads x 256 dims x 2 (QK and AV) x 1,048,576 = about 30 billion multiply-adds per token, to 1.4 billion for all the linear layers. At a million tokens attention is roughly twenty times the arithmetic of the rest of the model, and the cache is about four and a half times the weight traffic (14.0 GiB against 3.2 GiB). The layout fixes capacity. It does not make the full layers linear.



## The three thinking modes are a template switch

The card says "three configurable thinking levels, none, low, high". I expected a trained budget or a control token. The mechanism is in `chat_template.jinja`, and it is smaller than that. I rendered the repository's template with jinja2, and it gives these generation prompts for a user message `Q` (line breaks added for reading):

```text
none : <｜start▁of▁sentence｜><|System|>
       you are a helpful assistant.<｜end▁of▁sentence｜>
       <｜start▁of▁sentence｜><|User|>Q<｜end▁of▁sentence｜>
       <｜start▁of▁sentence｜><|Bot|></think>

high : <｜start▁of▁sentence｜><|System|>
       you are a helpful assistant.
       `thinking_effort` guides on how much to think in your thinking channel
       (not including the response channel), supported values include `low` and `high`.
       Now the system is invoked with `thinking_effort=high`.<｜end▁of▁sentence｜>
       <｜start▁of▁sentence｜><|User|>Q<｜end▁of▁sentence｜>
       <｜start▁of▁sentence｜><|Bot|><think>

low  : the same, ending `thinking_effort=low`
```

- **none** is `enable_thinking=false`. The template appends `</think>` straight after `<|Bot|>`, so the model starts its turn with the think block already closed. Nothing is trained into the weights that I can see from here; it is the prefill that does it.
- **low** and **high** both open `<think>` and differ only by one sentence in the system message. High is the default. Any other value for `reasoning_effort` raises an error in the template.

So there is no token budget and no hard cap: "low" is a request, in words, that the model is meant to honour through post-training (the card does not say how it was trained). Whether it does is a measurement, and the one I could make is in the next section. The README's recommended sampling is temperature 1.0, top-p 0.95, no top-k, and its example sets `max_new_tokens=131072`.

One consequence for anyone serving it: the server must render the template with `enable_thinking` and `reasoning_effort` passed as chat-template kwargs. The SGLang command in the card uses `--reasoning-parser qwen3`, which splits on `<think>` and `</think>`, and the card's client example shows `chat_template_kwargs: {"enable_thinking": false}` for none. I did not find a documented way to pass `low` there; it is the template's `reasoning_effort` variable.

## What I ran, and how far to trust it

The model needs `trust_remote_code`, and I did not execute the repository's Python. Instead I wrote a 150-line forward pass in plain PyTorch 2.14.1 (CPU, two threads of a shared four-vCPU box) from `modeling_spark.py` and `config.json`, and streamed the weights from the Hub with HTTP range requests so that nothing but the tokenizer and template touched disk. The prompts are rendered with the repository's own `chat_template.jinja` and tokenised with its `tokenizer.json`.

What differs from a reference run, so you can discount accordingly:

- **Weights are int8**, per output channel, including the tied embedding. A bf16 copy would need 3.4 GB of RAM, more than I could spare. For batches of tokens (prefill) the matmul is bf16 activations against the int8 values with the scale applied after; for single-token decode it is PyTorch's dynamic int8 path, which also quantises the activation per token.
- **The cache** is stored in bf16, and window layers keep only the last 511 earlier tokens, as the config's window of 512 implies.
- **Not validated against the reference code.** My checks: the model answers "The capital of Anhui Province is **Hefei**", and prefilling the same 700 tokens as one chunk or as chunks of 128 gives logits that differ by at most 0.24, with the same argmax. A first version used per-tensor activation quantisation in prefill and differed by 8.4 between the two chunkings, so I threw it and its one partial result away. A subtle bug that leaves the model coherent would not show up in either check.

Speed on this box, **measured**: single-stream decode ran at 5.2 to 5.9 tokens per second; prefill at 112 tokens per second for a 9.9k-token prompt, falling to 66 for a 40k one as the seven full layers' quadratic term grows. These say nothing about a GPU or Apple silicon.

### Thinking modes on ten small problems

Ten prompts with known numeric answers (17 x 23, the sum 1 to 100, bat and ball, lily pads, a remainder, a rectangle, the 5-machines puzzle and so on), each ending "Give the final answer as 'Answer: &lt;number&gt;'". One sample per prompt per mode at the recommended temperature 1.0, top-p 0.95, seeds 0 to 9; the token cap was 600 for none, 1,500 for low and 2,500 for high. A run that hit the cap before answering counts as wrong.

| Mode | Correct | New tokens, total | Mean | Median | Decode time |
|---|---|---|---|---|---|
| none | 8 / 10 | 953 | 95 | 87.5 | 188 s |
| low | 9 / 10 | 1,336 | 134 | 78.5 | 227 s |
| high | 8 / 10 | 3,734 | 373 | 117.5 | 673 s |

<ThinkModes />

Read this as a smoke test: ten easy items, one sample each, so one flipped answer is the noise floor. What I take from it:

- **Mode changes length more than accuracy, and mostly through one prompt.** The high-mode mean is dragged up by the 5-machines puzzle, where it thought for the full 2,500 tokens and never answered. Without that prompt the high and low means are 137 and 78 tokens. The medians, 78.5 for low and 117.5 for high, are closer to the typical gap.
- **None is not "no reasoning".** It writes the working out in the answer, 95 tokens on average, and still got the machines puzzle wrong ("100 minutes"). The think block being closed does not stop the model from reasoning in the visible reply.
- **Low thinking is terse.** On the lily-pad prompt, low wrote "Patch doubles daily, takes 48 days to cover whole lake. ... Half would be after 47 days" and answered 47. High on the same prompt wrote "Half at day24 (since 2^24 half)" and answered 24. Different samples of one model, not evidence about the levels, but it shows what high does not buy on a trap question.
- **Low also failed on the machines puzzle** (635 tokens, answer 500, after computing 5 correctly once along the way).

So the claim I can support is narrow: the three settings produce three different token budgets, in the order the card implies, and on easy problems the extra thinking did not improve the score. I did not test hard problems where thinking should pay.

### Needle probe out to 40k tokens

One synthetic haystack per length: random sentences of the form "The quiet lantern measured the old harbour near the falcon on day 212". Five lines of the form "The secret code for vault Orchid is 240891." are planted at 10, 30, 50, 70 and 90 percent of the way through. After prefilling the haystack once, I ask for each vault in turn from the same cache, with thinking off and greedy decoding, and score exact match of the six digits.

<NeedleGrid />

| Prompt tokens | Prefill (2 threads) | Exact | Cache, measured |
|---|---|---|---|
| 9,871 | 88 s | 5 / 5 | 163,487,744 bytes |
| 20,008 | 205 s | 5 / 5 | 308,811,776 bytes |
| 40,256 | 612 s | 4 / 5 | 599,087,104 bytes |

The one miss is a near miss: asked for vault Basalt at the 30 percent mark in the 40k haystack, it answered `1696853` for the true code `696853`, an extra leading digit. The cache sizes are the actual bf16 tensors held after prefill, and they equal the formula above to the byte (40,256 x 14,336 for the seven full layers, plus 21 x 511 x 2,048 for the windows), which is a check on my layout reading and not on the model.

What this does and does not show. Retrieval of a distinctive line through the seven full layers works at 40k tokens, which is already about 79 times the 512-token window, so something in those layers is attending far. It is a weak test: the needle is lexically unlike the filler, there are only five needles, no distractors resemble them, and the question is a direct lookup. It says nothing about the reported hard buckets, multi-hop Graphwalks or the 512k-to-1M MRCR, and I did not reach 100k, let alone a million: at the speed I measured, a million-token prefill on this box would take many hours (**reasoned**: more than 4 hours even at the 66 tokens per second of the 40k run, and the rate keeps falling), and its 14 GiB cache would not fit in the RAM I had.

## Where this leaves a reader

- **The window is a memory claim first.** A million tokens fits in 14.0 GiB of bf16 cache because three layers in four hold 21 MiB however long the context is. That is a real engineering choice, and on the 4B (36 layers, nine of them full, 16 query heads over 4 KV heads) the same pattern holds. It does not make attention cheap: at a million tokens each decoded token still reads the full-layer cache and does about twenty times the arithmetic of the weights.
- **The reported long-context jump is post-training.** X2.5 and X2.6 share an architecture and the card's own table moves MRCR 512k-1M from 0.9 to 19.9. I could not test that range, so I treat it as **reported**.
- **Thinking is a prompt, so you control it.** If you serve the model yourself, `enable_thinking` and `reasoning_effort` are chat-template variables. A server that does not forward them runs the default, which is high, and you will see long outputs.
- **Quantised files exist for every common runtime** (FP8, INT8, INT4 safetensors, three GGUFs), with the embedding left at bf16 in the safetensors variants. I downloaded none of them; my numbers are for my own int8 conversion of the bf16 weights.
- **What I would check next:** run the bf16 model with the reference code on a GPU and compare my logits; a needle test with distractor vaults; the 128k bucket on a machine with the memory for it.

The card's licence is Apache-2.0, and I read the `LICENSE` file, not just the front matter. The lab's relationship to iFlytek I could not verify, so I leave it out.
