LayerFS is a filesystem for agents. Each agent gets a complete, writable copy of a project, the copy costs almost nothing to make, and what the agent changes is saved as a commit on a branch in a store every agent shares. The README sells ten ideas. One of them is a number: **157 snapshots of a real project in 100 MB, 19.9x smaller than Btrfs with zstd**. The author's announcement post says the same thing in French. I could not open the post (the page returned HTTP 402), so I work from the README and the research notes in the repository, which carry the numbers.

This article does four things. It reads the code to say what the store actually is. It rebuilds the idea as a small Python toy and measures it on 157 commits of a repository I have, with real byte counts. It then runs the real store, in process, over the same 157 commits, and corrects the toy where the two disagree. And it says plainly whether the 157-in-100-MB claim could be checked from here. It could not, and the reasons are below.

## What problem it is aimed at

An agent that edits code needs a working directory, and parallel agents need one each. A `git worktree` per agent drops `node_modules` and build output, and a copy is a copy. LayerFS mounts one shared committed tree as a **Workspace**: writable, with its own overlay for changes. When the command finishes the changes are committed and the mount goes away. If every tool call becomes a commit, history grows by one snapshot per call, and the question is what a snapshot costs.

## The model, as the code and docs state it

This section is **read**, from `docs/general/concepts.md`, the `core/` crates and the `engine/` crates; where a line was later run it says so.

- **Store.** One SQLite file holds every branch, commit and content object. Daemons and the SDK open it directly; there is no database server. The store runs in a "Disposable" profile only, with no crash or power-loss durability. The README says this itself.
- **Layer, branch, commit.** A layer is an immutable published snapshot. A branch is a named writable line based on a layer. A commit is an immutable snapshot of a branch. Publishing a branch to `main` adds a layer. Forking a branch and publishing a layer reuse existing roots and copy no payload.
- **Workspace.** An ephemeral view of one branch head. `layerfs-overlay` describes itself as "one Workspace's disposable SQLite database". Commit captures the final state and publishes with a compare-and-swap on the branch head. End never commits implicitly, and a clean End refuses uncommitted state.
- **Objects.** Files and trees are immutable canonical objects. An object's ID is a BLAKE3 digest over a frozen domain separator (`layerfs/object/v2`) followed by the canonical bytes. Objects are append-only; inserts deduplicate on the ID; normal operations never delete.

### The chunker

A file is cut into pieces by content, so that an edit disturbs only the pieces around it. `file/cdc/gear.rs` is a frozen two-byte rolling GEAR chunker, and its parameters are constants:

| parameter | value | source |
|---|---|---|
| minimum chunk | 8,192 bytes | `MINIMUM_CHUNK_BYTES` |
| target | 16,384 bytes | `TARGET_CHUNK_BYTES` |
| maximum | 32,768 bytes | `MAXIMUM_CHUNK_BYTES` |
| normalization shift | 2 | `NORMALIZATION_SHIFT` |

The first 8 KiB of every chunk are skipped without scanning. A stricter mask applies below 16 KiB, a looser one above, and a boundary is forced at 32 KiB. Two consequences, **reasoned** from the code: a file under 8 KiB is always one chunk; and a boundary depends only on the bytes since the previous one, so the chunker resynchronizes after an edit.

**An earlier version of this section stopped there and got the policy wrong.** The chunker is not applied to every file. `DEFAULT_SMALL_FILE_THRESHOLD_BYTES` is 131,072: a nonempty file up to 128 KiB is stored as one **whole-file object**, and only a larger file goes through the GEAR chunker. The finished Store records it in `store_policy` (**measured**, below), along with delta depths of 16 for whole files, 8 for chunks and 8 for metadata. In the real run, 4,281 whole-file objects held 66.9 MB of canonical bytes and 1,416 chunks held 23.7 MB. About a quarter of the content ever went through the chunker.

The profile is frozen on purpose: changing any constant or table entry changes every chunk identity, so `profile_id()` hashes all of them.

### Trees, pages and encodings

Directories and file-to-chunk maps are also objects. From `filesystem/limits.rs` (**read**): a page is at most 8,192 bytes; an inode leaf holds 50 to 100 rows; a branch holds 64 to 127 children. That is a wide, shallow, B-tree-shaped structure, which matters for the next section: changing one file rewrites one leaf and the path of branches above it, not the whole directory.

Objects are then packed. `layerfs-storage` has four pack lanes (ordinary, chunk, whole-file, singleton). Payload frames are compressed with zstd level 3. Groups of value records are compressed with level 1 and capped at 65,536 bytes. A stored record can be a FULL representation, a PREFIX (a payload encoded against a base payload) or a DELTA against another object. The project's own report counts 28,106 FULL and 58,306 PREFIX records and 4,583 inode-leaf DELTAs in its September research run (**reported**).

### Merge

Merging is three-way over immutable roots (`merge/`, **read**). Two commits that change the same file are refused with `Conflict` unless a rule says otherwise. The conflict kinds in `ConflictKind` are `Content`, `AddAdd`, `ModifyDelete`, `DeleteModify`, `Type`, `Binary`, `Markers` and `Mode`. Text files get a line-level three-way merge with markers. Anything binary keeps "ours" unmarked and reports a conflict. A `/.lww` file holds gitignore-style patterns; a path both sides changed that matches takes the side with the newer modification time, ours on a tie. That is the escape hatch for lockfiles and build outputs, where two agents will always collide and no human wants to resolve it.

The storage side is where the claim lives.

## The claim, and what it would take to check it

The README's results table says (**reported**): "A real project's history, 157 snapshots (4.94 GB of trees), kept as mountable Commits. 100.1 MB vs 1,994.6 MB, 19.9x smaller than Btrfs + zstd; 156/156 read back."

The arithmetic holds. 1,994.6 / 100.1 = 19.9, and 4,936,693,030 logical bytes over 100.1 MB is 49.3 to 1. The note beside the table says one sample per case, an arm64 Mac running Docker Desktop, 8 CPUs, 8.3 GB.

A second document, `docs/research/layerfs-vs-btrfs-157/REPORT.md`, covers the same 157 checkpoints in September. Its LayerFS figure is **184.6 MB**, from an earlier research candidate, and its ratio against the same Btrfs baseline is **10.81x**. So the headline moved by a factor of 1.8 between that candidate and the 1.0.0 release (**reported**). The README links the report.

The workload is **157 Git tree states of DeepSeek Harness**, picked at ordinals 100, 200, ... of 15,632 commits, with `.git`, dependencies and build output excluded. 904,143 path occurrences, 4.94 GB of logical content, 891.9 MB of unique Git blob bytes. About 65% of unique file contents are under 8 KiB. Changed files are rewritten in full on every step, 181,002 writes totalling 1.72 GB, with no hardlinks, reflinks or byte-range patches helping either side.

Could I check it? No, for three separate reasons.

1. **I did not run LayerFS.** I read the Rust and did not build the workspace. The real thing mounts through FUSE in a Linux daemon, and the project's own runs used Docker Desktop on a Mac.
2. **I do not have the inputs.** The frozen manifest points at 15,632 commits of another repository, and its unique blobs alone are 892 MB. My scratch budget for this article was 600 MB.
3. **The comparator is not mine either.** The Btrfs numbers came from loop devices in a privileged container, with `compress=zstd:3` and metadata DUP.

What I can say from the report itself, **reported**: the authors flag that LayerFS's figure is a full-store allocation including indexes, that Btrfs's includes DUP metadata copies, and that the two "are not identical whole-device accounting" and do not establish equal durability. Their ranking of Btrfs is also workload-bound: on a separate 512 MiB file, changing 4 KiB through a Btrfs snapshot cost about 36 KiB. They say this does not transfer to the small-file history.

So the claim is a specific, carefully caveated measurement of one workload. What I could do is ask whether the *idea* behind it produces numbers of that size on a different workload.

## Experiment: a toy of the layer-and-dedup idea

The setup, all **measured**:

- Workload: **157 commits sampled evenly, oldest to newest, from the git history of this site's repository** (728 commits over 19 days), with `public/` excluded because it is 1.6 GB of images and video that are not what the experiment is about. 569,351 file occurrences, **7,795,062,839 logical bytes**. Different workload from LayerFS's: a Next.js site with MDX, TypeScript, JSON and vendored JavaScript, not DeepSeek Harness.
- Only 4,525 distinct files (by git blob) appear across the 157 snapshots, 132,433,378 bytes in total.
- The toy chunks each distinct file with a Python port of the frozen GEAR chunker, reading the 256-entry table and the four masks out of `gear.rs`. Files of 8 KiB or less are one chunk. **This was the toy's mistake**: the real store chunks only above 128 KiB (see "What running it showed"), so the toy chunked 2,333 distinct files where LayerFS chunks 243 and keeps the other 2,090 whole. Chunk IDs are SHA-256 (the real store uses BLAKE3). Each unique chunk is compressed on its own with zlib level 6. **zlib stands in for zstd everywhere** (my Python has no zstd), so ratios between rows are meaningful and absolute sizes will not match LayerFS.
- The toy stores each directory as an object listing its entries and each file's chunk IDs, and addresses that object by hash, so an unchanged subtree is stored once. Each snapshot adds a 100-byte commit record. Every object carries 36 bytes of index cost. That is a git-like Merkle tree, not LayerFS's paged one.
- Comparators: plain copies (sum of file sizes); a hardlink farm (each distinct file once, uncompressed, directory entries not counted, which flatters it); one `tar.gz` per snapshot; and one `tar` of the distinct files through xz.

The port was first checked only for shape: on 3,002 chunks from large files the mean chunk was 19.8 KB, p10 12.6 KB, p50 18.7 KB, p90 28.9 KB, with 5.4% cut at the 32 KiB maximum. The real run later gave a second check, a weak one: the real store cut the two large files into 88 and 49 chunks, the same counts my port produced. I did not compare the boundaries one by one.

| representation | bytes | against plain copies |
|---|---:|---:|
| plain copies | 7,795,062,839 (9.00 GB in 4 KiB blocks) | 1.0x |

The `tar.gz` row is a scale: I summed per-file zlib sizes over every snapshot (3,175,421,219 B) and multiplied by 0.895, the ratio I measured on the last snapshot between a real `tar.gz` (19,623,863 B) and the same files compressed one by one (21,923,627 B).

Three readings.

**The hardlink farm gets most of the way.** On this workload 59x comes from storing identical files once, because the snapshots are mostly the same files. A headline against plain copies would be uninteresting, which is why the project compares against Btrfs.

**Compression is the next factor of three, and chunking is the smallest.** Compressing the distinct files takes 132 MB to 38.6 MB (3.4x). Chunking cuts the raw bytes you must hold by 44% (73,793,323 against 132,433,378, because a changed large file shares most of its pieces with its previous version), but after compression the payload falls only from 38.6 to 27.5 MB, 29%. Compression had already removed much of the redundancy chunking would have removed. For a text-heavy workload like this one, that is a reasonable result; for big binaries, where compression finds little, I would expect chunking to matter more. That last sentence is **reasoned**, not measured. The real run changes the picture further: LayerFS chunks only a quarter of the bytes, and what saves it the rest is encoding each changed file against its predecessor.

**The archive beats the toy.** One xz archive of the distinct files is 20.4 MB, half the toy's 41.6 MB. It is also a single file with no random access, no history structure, and no way to mount a snapshot. The toy pays for those properties, and the next experiment shows where.

## Experiment: the edit that touches a big file

The README's idea ten is "an edit costs the size of the edit, not the size of the file." With a content-defined chunker, an edit rewrites the chunks around it. I took the two largest files in the sampled history (a 1.70 MB JavaScript example and the 0.99 MB minified p5.js this repository vendors), applied a 100-byte edit to the middle, chunked again, and counted chunks whose hash is new. **Measured:**

<ChunkEdit />

| file | edit | new chunks | bytes in them |
|---|---|---:|---:|
| 1.70 MB, 88 chunks | overwrite 100 bytes | 1 | 22,538 |
| | insert 100 bytes | 4 | 74,492 |
| | append 100 bytes | 1 | 4,540 |
| 0.99 MB, 49 chunks | overwrite / insert / append 100 bytes | 1 / 1 / 1 | 21,697 / 21,797 / 16,187 |

These are the toy's numbers. The real store's are in the next section, and they are smaller. An overwrite costs one chunk, 1.3% of the larger file. The insert into the first file cost four, 4.4% of it, where the second file needed one. I did not know why the first file resynchronizes slowly and suspected a port bug; the real store, run on the same bytes, also touched three chunks for the insert, so the port is probably not to blame, but I still have not compared boundaries. What the numbers support is narrow: edits of this size to files of this size store tens of kilobytes, not megabytes, before compression. They do not say that the cost is "the size of the edit", which here is 100 bytes. The floor is one chunk, 8 to 32 KiB. For an edit loop of small changes that is roughly a 200x amplification of the edit and a 75x saving against the whole file.

## Where the bytes go: structure, not payload

The ledger above hides the most interesting number in the toy. Split the 41.6 MB by what it is made of:

- chunk payload: 27,500,226 B (66%)
- flat directory objects plus commit records: 14,061,679 B (34%)

And the growth later in the history is worse for structure. Between snapshot 80 and snapshot 157 the toy grew by **145,942 B per snapshot**, of which payload was 52,979 B and directory objects 92,863 B. Directory structure was **63%** of the marginal cost of a snapshot. The first snapshot itself, 18.5 MB, is almost all payload (18.27 MB).

The reason is simple. Over the 157 snapshots the repository has 569,351 file occurrences, roughly 3,600 files in each. A snapshot changes a handful of them. But in my toy a directory is one object, so changing one file in a directory with 300 entries writes the whole 300-entry listing again, with every file's chunk IDs. The big directories are the ones that change most, so it happens often.

LayerFS does not do this (**read**): leaves hold 50 to 100 rows and branches hold 64 to 127 children, and a leaf can be stored as a delta against its predecessor. So I changed the toy. In the second variant a directory's sorted entries are split into pages with boundaries chosen by a hash of the entry name, about 64 entries a page, and the directory object lists page IDs. A one-file change rewrites one page plus the small directory object.

<StructureCost />

**Measured:** paged directories cost 4,577,755 B against 14,045,979 B flat. The total at 157 snapshots drops from 41.56 MB to **32.09 MB**, and the marginal cost per snapshot after snapshot 80 from 145,942 B to 80,684 B. Structure falls from 34% to 14% of the store.

Now put LayerFS's own breakdown next to it. From the September report (**reported**), the 184,598,528-byte store is made of 98,256,041 B of payload groups (53%), 56,719,413 B of structure groups (31%), 378,096 B of pack headers, 26,357,298 B of database outside the packed blobs, and 2,887,680 B unattributed. The structure share, 31%, is the same size as my flat toy's 34%. It is a different workload and a different representation, so I draw no tight conclusion. The reading I will defend is this: in a history of small files with many snapshots, **a store's size is decided at least as much by how it encodes the tree as by how it deduplicates the files**. The report says as much about Btrfs: its metadata region was 1,293.8 MB of the 1,994.6 MB baseline, and a dedup tool that shrank data by 53% grew metadata by 414 MB and made the total worse.

If the 1.0.0 release got from 184.6 MB to 100.1 MB, I did not read how, and I will not guess at the mechanism.

## What running it showed

Everything in this section is **measured** on this machine, 31 October, at LayerFS commit `35d3657` (rustc 1.97.0, a shared 4-core VM, no root). The scripts, raw JSON and the exact commands are in `public/articles/layerfs/verify/` (`RUN.txt` first).

**What can run here.** `core/` (content, storage, history, telemetry) is plain Rust with no mount. So is most of `engine/`: the project importer, the SQLite persistence layer, the overlay and the store service that turns a Workspace's changes into a Commit. Only `layerfs-fuse`, the daemon and the sandbox need `/dev/fuse` and root, and I did not run them.

**What I ran.**

1. `cargo test` on four test files of `layerfs-content` that pin the frozen profile, the page limits, the object identity and the chunker: 21 tests, all passed.
2. A small crate of mine, with path dependencies on the LayerFS workspace, that follows the project's own test fixture. Snapshot 0 of the 157 is imported into a fresh Store with `layerfs_project::init` and the frozen default policy. Each later snapshot is applied as one `fs.apply` call (remove, `mkdir`, write for every path that changed) on a fork of `main`, which is a private Workspace and a real Commit. 156 Commits, about 70 seconds. It is the product's commit path with the mount left out.
3. The same 157 commits as the toy, and the toy confirmed it: 569,351 file occurrences, 7,795,062,839 logical bytes, 4,525 distinct blobs. The Store's own `store_totals` row says `logical = 7,795,062,839`, to the byte.

**The result.** The finished Store file is **27,607,040 bytes**: 19.1 MB for the first snapshot, 8.5 MB for the other 156. That is 282 to 1 against the logical size.

| store | bytes | against logical |
|---|---:|---:|
| **real LayerFS Store, 157 snapshots** | **27,607,040** | **282x** |
| toy, first version: chunks above 8 KiB, flat directories, zlib | 41,561,905 | 188x |
| toy, first version: paged directories, zlib | 32,093,681 | 243x |
| toy rerun with the real 128 KiB cutoff, zstd level 3, flat | 42,110,305 | 185x |
| toy rerun with the real 128 KiB cutoff, zstd level 3, paged | 34,322,310 | 227x |
| one `tar` of the distinct files through xz | 20,388,344 | 382x |

So the real store is 20% under the rerun's paged toy, 14% under the first one, and 1.35 times the xz archive. My verdict in the first version, that the idea is sound and the size is plausible, stands. The toy was too pessimistic, and for two reasons the run made visible.

**Where the bytes are.** The Store's own accounting (`store_totals`) gives 98.0 MB of canonical object bytes, of which 25.2 MB were stored. Split the file: payload packs 23.73 MB (86%), metadata value-group packs 1.45 MB (5%), SQLite tables, indexes and page slack 2.43 MB (9%). Everything that is not payload is 3.88 MB, **14%** of the file. That is the share my paged toy reached (14%) and far from the flat toy's 34%, so the structure result holds up: a paged, shallow tree is what keeps structure small. (The first version's argument that structure decides a store's size is the part of this article that the real run supports most directly.)

**Correction one: the chunker's reach.** Covered in the chunker section above. Files up to 128 KiB are whole-file objects. Re-running the toy with the 128 KiB cutoff raised the raw chunk bytes it holds from 73.8 MB to 87.8 MB and barely moved its total (zlib flat 41.10 MB against 41.56 MB), so the cutoff alone does not explain the gap between toy and store.

**Correction two: it stores edits against the previous version.** The toy wrote every changed file in full, compressed on its own. The real store's payload is 23.73 MB against the toy's 30.3 MB, and the edit runs show why. I wrote a base file, then an edited copy of it, and read the Commit's own `newStored` counter:

| file | 100-byte edit | stored by the edit | chunks stored (full / delta) |
|---|---|---:|---:|
| 1.70 MB JavaScript (88 chunks) | overwrite | 7,584 B | 0 / 3 |
| | insert | 3,822 B | 0 / 3 |
| | append | 3,635 B | 1 / 0 |
| 0.99 MB `p5.min.js` (49 chunks) | overwrite | 3,720 B | 0 / 4 |
| | insert | 2,586 B | 0 / 3 |
| | append | 2,336 B | 1 / 0 |
| first 200,000 bytes of the 1.70 MB file | overwrite / insert / append | 10,087 / 1,164 / 977 B | 0 / 3, 0 / 3, 1 / 0 |
| first 100,000 bytes (a whole-file object) | overwrite / insert / append | 438 / 440 / 434 B | no chunks |
| first 20,000 bytes (a whole-file object) | overwrite / insert / append | 435 / 437 / 431 B | no chunks |

A 100-byte edit to the 1.7 MB file stored 3.6 to 7.6 KB, against the 22 to 74 KB the toy counted as new chunks before compression. A 100-byte edit to a 100,000-byte file stored **438 bytes**. The toy would have stored that file again, and the real store's own charge for the base was 74,855 B. The storage README and the codec describe the mechanism (**read**): a record can be FULL, or a PREFIX or DELTA against a base object, and the complete framed record cost decides. What I measured is the effect, not which branch each record took. The first edit above is the largest (7.6 KB); I did not chase why a 100-byte overwrite touched three chunks rather than one.

**Growth per snapshot.** The Commits stored a median of 40.5 KB and at most 646 KB. After snapshot 80 they averaged 41.2 KB each by the store's own counter, against 81 to 95 KB for the paged toy and 147 KB for the flat one. Counting the SQLite file instead of the counter, the 156 Commits added 54.5 KB each on average, against 46.6 KB by the counter over the same Commits: the pages and indexes around the objects cost about 15% more than the counter shows.

**Read-back.** I read every file of the last snapshot back through `fs.read`. All 3,929 text files came back with the size git has, and the 3,864 that fit in one reply matched git's bytes exactly. The other 45 are binary and `fs.read` refuses them as text, so I have not checked those bytes. This is a spot check of my run, not their 156/156.

**The parameters the article states, against the code.** All confirmed by reading `gear.rs`, `limits.rs`, `codec.rs` and `policy.rs`, and by the tests: chunk size 8,192 / 16,384 / 32,768, normalization shift 2, pages up to 8,192 bytes, inode leaves of 50 to 100 rows, branches of 64 to 127 children, payload frames at zstd level 3, value groups at level 1 and capped at 65,536 bytes, four pack lanes. The one thing the article had missing was the 128 KiB cutoff above.

**Garbage collection.** I said I found none. The README says the Store only grows, and the only reclamation I found in the persistence layer returns free SQLite pages and leaves "logical objects unchanged". That is now **read**, not reasoned. The run did not exercise it.

**What this does not settle.** The 100.1 MB headline is on a private input, DeepSeek Harness, and the 1,994.6 MB comparator is Btrfs with zstd on loop devices in a privileged container. I have neither, and loop devices need root. My 27.6 MB is on a different history, so 282x against their 49x says that this history is far more repetitive, not that either number is wrong. I have not reproduced their number and nothing here should be read as doing so.

## What this does and does not say about 157 in 100 MB

My toy reached 41.6 MB flat and 32.1 MB paged on a **different** repository, and the real store reached 27.6 MB on the same one. That is neither a confirmation nor a contradiction of the 100.1 MB. The ratio to logical size is 188x to 243x for me against 49x for LayerFS, which would be an alarming difference if the workloads matched. They do not, and the comparison I find fairer is the shape of the results rather than the ratio:

- My snapshots are larger on average (7.795 GB / 157 = 49.7 MB against LayerFS's 4.94 GB / 157 = 31.4 MB), but my history is text-heavy and comes from an actively edited repository with very few large new files.
- Snapshot spacing differs. LayerFS picked every hundredth commit of 15,632; I sampled 157 of 728, about 4.6 commits apart. Closer snapshots change less between steps, which should make mine cheaper.
- My 36 bytes of index per object was a guess, and it was low: in the real store the locator table alone costs about 55 bytes an object (503,808 B of pages over 9,160 objects), before the inode table and the other indexes. Their 18.7 MB of objects-index pages is 10% of their research store.

So the honest verdict is: **the idea is sound and the size is plausible, the claim is unchecked.** A content-addressed, chunked, tree-structured store with delta encoding should land well below a hardlink farm on this kind of history, and my toy did. A content-addressed, chunked, tree-structured store with delta encoding did land well below a hardlink farm (132 MB, 27.6 MB for the real store). Whether it lands at 100.1 MB on the 157 DeepSeek Harness states, I cannot say.

## What it costs

From the project's own pages (**reported**), without my reproduction:

- **No durability.** The Store runs in its Disposable profile only. Use it for agent work and its history, not as the only copy of anything you cannot rebuild.
- **Sequential writes are slow.** In the fio suite the README lists 0.31x for sequential write, 0.81x for sequential read and 0.40x for random write against libfuse passthrough, while random read/write mixes ran 1.49 to 2.23x. A build that writes big artifacts through a mount will feel the first number.
- **Not full POSIX.** The FUSE view omits FIFOs, sockets, device nodes, set-id bits and separate atime/ctime. pjdfstest shows zero unexpected failures but keeps 76% of overlayfs's passes.
- **Compact encodings cost reads.** The research report says compact representations can require decoding and dependency traversal, and that its capacity comparison does not price that in.

And a cost I **reasoned**: by design every tool call becomes a commit, so the history is as long as the agent's activity, and the store only grows because objects are never deleted in normal operation (**read**: the README says it). 41 KB to 55 KB per snapshot in the real store is small for 157 snapshots and is not small for 157,000. I found no garbage collection, only the return of free SQLite pages.

## What I'd take from it

If you run several agents on one codebase, three things in LayerFS are worth copying even if you never use the product.

1. **Separate payload from structure when you measure storage.** My flat toy and my paged toy have identical payload bytes. They differ by 30% in total size. In the real store everything that is not payload is 14%.
2. **Check what your snapshot gap is before comparing.** A ratio at every-fifth-commit and a ratio at every-hundredth are not the same experiment.
3. **Compare to the archive.** A single xz of the distinct files was 20.4 MB. If your store is within 2x of that and gives you mountable, branchable history, it is doing its job. The real one was at 1.35x.
4. **Check the policy before you port the algorithm.** My port of the chunker was faithful, and still modelled the wrong store, because the chunker only runs above a cutoff I had not read.

The code is MIT licensed and core has no engine dependencies, which made the chunker easy to read and port: one 567-line file, most of it the GEAR table.

## Reproduce the toy

The script is `public/articles/layerfs/toy_store.py` in this site's repository. It needs Python 3, `git`, a repository to sample and the `gear.rs` file from a LayerFS checkout, and it writes `result.json`. It holds every distinct file in memory (132 MB for my run) and took a few minutes on a shared 4-core VM at low priority.

```bash
git clone --depth 1 https://github.com/Ephemeral-AI-Lab/layerfs
nice -n 19 python3 -I toy_store.py 157 /path/to/repo layerfs/core/crates/layerfs-content/src/file/cdc/gear.rs
```

The core of it is the chunker. This is the port, trimmed to the loop:

```python
def cdc(b):                      # frozen profile: min 8192, target 16384, max 32768
    n, out, s = len(b), [], 0
    while s < n:
        if n - s <= MIN: out.append((s, n)); break
        pos, h = MIN, 0          # the first 8 KiB of a chunk are skipped unscanned
        while True:
            a = s + pos
            if pos >= MAX: cut = a; break
            if a + 1 >= n: cut = n; break
            small = pos < TGT    # stricter masks below the target size
            h = ((h << 2) + (GEAR[b[a]] << 1)) & M64
            if h & (SSMALL if small else SLARGE) == 0: cut = a; break
            h = (h + GEAR[b[a + 1]]) & M64
            if h & (SMALL if small else LARGE) == 0: cut = a + 1; break
            pos += 2
        out.append((s, cut)); s = cut
    return out
```

## Reproduce the real-store run

`public/articles/layerfs/verify/` has the crate (`lfsverify_main.rs`, `lfsverify_edits.rs`, `lfsverify_Cargo.toml` with the checkout path left as a placeholder), the raw outputs and `RUN.txt`. Build it against a LayerFS checkout at `35d3657` with `cargo build --release`, then run `lfsverify 157 <repo> 616e70dc <workdir>`. Use any git repository and any revision; the 157-commit sample, the exclusion of `public/` and the result JSON are the same shape. It took about 70 seconds and a few hundred megabytes of disk once built; the build itself took a few minutes.

## What I did not do

- I did not mount LayerFS. No FUSE, daemon or sandbox crate ran, so nothing here says anything about mount cost, read latency or the fio numbers.
- I did not check the 157-snapshot figure of 100.1 MB, the 19.9x ratio, the Btrfs numbers or any benchmark in the README. The input is private and the comparator needs root.
- I did not run Btrfs, so my 27.6 MB has no comparator of mine.
- I did not read the announcement post, so I do not quote it.
- I did not compare my chunker port's boundaries with the Rust ones, only the chunk counts of two files.
- I did not read the release notes on how the store went from 184.6 MB to 100.1 MB.
- I did not test merge, `.lww` or concurrent agents, only read their types and docs.
- Snapshots went in through `fs.apply`, not through a mounted tree: modes other than the executable bit were not set, symlinks were written as small files, and a directory a snapshot emptied stayed as an empty directory.
- I did not run the rest of the test suite, only four test files of the content crate.

An independent check is cheap for someone with a Linux box and Docker. Run the project's `dsh-dedup` suite from `layerfs-benchmark` and compare its receipts to the table in the README. I would be glad to read that.
