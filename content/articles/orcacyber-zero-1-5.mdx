This morning [OrcaRouter announced](https://x.com/OrcaRouter/status/2108802238567354864) OrcaCyber Zero 1.5, "our latest frontier cybersecurity model, built to discover critical vulnerabilities, investigate complex attack paths, and validate real-world exploitability." The post lists four results: 95.8% on CVE-Bench "(23/24 evaluable tasks)", 100% on Cybench "(39/39, unrestricted)", 93.9% on HumanEval+, and, for the system its predecessor powered, "98%+ pass@1 on CyberGym, ranking among the top 3 globally." It is "Available now exclusively on OrcaRouter."

This site has run into OrcaRouter before, mostly as a publisher of refusal-ablated open models: [GLM-5.3-Flash-Uncensored](/articles/glm-5-3-flash-uncensored), the [runtime abliteration of Ternary Bonsai](/articles/runtime-abliteration), and quantizations like [OrcaSAQ-2](/articles/qwen3-8-27b-variants). This is the first time it has released something it calls a frontier model of its own. A 100% and a 98% next to each other is the kind of line I want to check before anyone repeats it, so I read the three security benchmarks' papers and code, pulled their public leaderboards, and found OrcaRouter's own technical report for the CyberGym run.

Two things surprised me. The CyberGym number is real, third in the leaderboard's own data, and not mainly a measurement of OrcaCyber Zero: another model ran every one of the 1,507 tasks, and Zero 1.0 was called in on 656. And 100% on Cybench is less extraordinary than it sounds, because a frontier lab already reported it. It is the conditions around these numbers that are missing, and they are what makes a security score comparable.

## What OrcaRouter has published

There is no paper, no model card in the usual sense, no system card and no weights. What exists is a model page on OrcaRouter's site, its machine-readable twin at `/api/public/models/orca/orcacyber-zero-1.5`, the thread under the launch post, and, for the predecessor, a CyberGym report on GitHub.

The predecessor's JSON is more specific. OrcaCyber Zero 1.0, released 17 September, is described as "a cybersecurity post-trained coding model", and its one benchmark is "CyberGym Level 1 pass@1", 98.07%, "(1,478/1,507)". Keep that 1,478 in mind.

## CyberGym: what a pass means

CyberGym is a large benchmark built from real bugs that OSS-Fuzz found in open-source projects. At level 1, the setting everyone reports, an agent gets the vulnerable source tree and a text description of the bug, and it has to produce one input that crashes the vulnerable build. The grader then runs the same input against the patched build. A pass means the input crashes the first and not the second, so the agent has to hit the specific bug rather than any crash. There are 1,507 such tasks. The paper's opening figure shows the setup:

/>

The number OrcaRouter quotes for the harness, 98.01%, is 1,477 of 1,507 in its own technical report. Zero 1.0's model card says 98.07%, which is 1,478. One task apart, so I take both as the same run reported twice, and I could not find which one was re-graded. Either way the score is real in the narrow sense that it is in CyberGym's leaderboard data, third behind 99.2 and 98.47.

What the report also shows is who did the work. The harness is a router over two models. DeepSeek V4 Flash runs every task. OrcaCyber Zero 1.0 is called in only when the router decides the worker has stalled, which happened on 656 of the 1,507 tasks. The report's cost table gives per-task means for both, so the split can be put on one footing:

<WhoDidTheWork />

Averaged over all 1,507 tasks, Zero 1.0 accounts for about 18% of the input tokens, 26% of the output tokens and 65% of the estimated cost. It is the expensive specialist that a cheaper model hands the hard cases to. That is a reasonable design, but it means "98% on CyberGym" is a measurement of the system, not of the model now being launched, and it is not a measurement of Zero 1.5 at all.

Two other facts frame the number. The same DeepSeek V4 Flash, inside another team's agent with no second model, scores 94.16. In DeepSeek's own agent it scores 76.7. So the agent around a model moves a CyberGym score by more than twenty points, which makes the harness the main thing being compared. And CyberGym itself has stopped ranking the top of its board: the leaderboard page now shows the twenty systems above 90% in random order, with the score "only for reference", and its submission guide from August says top systems have "nearly saturated" the benchmark.

## Cybench: 39 of 40, and what "unrestricted" leaves out

Cybench has 40 capture-the-flag tasks taken from four professional competitions, and it defines two ways to run them: unguided, where the agent gets one objective and has to find the flag, and subtask-guided, where the task is broken into steps with hints. "Unrestricted", OrcaRouter's word, is not one of Cybench's modes, and the page does not say which of the two it means, how many attempts each task got, or what the iteration cap was.

The claim is 39 of 39. Cybench has 40 tasks, so one was left out and the post does not say which. Counted as a miss, the same run is 97.5%. That alone is not damning: frontier labs routinely report Cybench on subsets of 35, 37 or 39 tasks, usually because a task's container is broken. And 100% is not new. Claude Mythos Preview's entry on the Cybench board is also 100%, on a 35-task subset; Opus 4.7 is 96 on the same 35.

The bigger problem with any high Cybench score in 2026 is contamination. All four competitions released their tasks between October 2022 and March 2024, before the training cutoff of every current model, and 31 of the 40 tasks ship a solution script in the public repository. The Cybench paper drew this exact comparison when it was published:

A model post-trained "for cyber" on public write-ups would be expected to do well here whatever its general ability, which is why a Cybench number without the run settings and the excluded task says very little.

## CVE-Bench: a denominator nobody else uses

CVE-Bench is 40 critical vulnerabilities in real web applications, each run in two settings: zero-day, where the agent gets no hint, and one-day, where it gets the public CVE description. A run passes when the grader observes one of eight defined attack outcomes against the sandboxed application. The paper's best agents in 2025 reached about 13%.

  caption="CVE-Bench scores against a set of defined outcomes in a sandbox (CVE-Bench paper, Figure 1)."

The claim is 95.8%, which is 23 of 24 "evaluable" tasks. Nothing in the CVE-Bench repository marks any task as not evaluable, so the 24 is OrcaRouter's own denominator and it is not explained. If the other 16 were failures, the run is 23 of 40, 57.5%. That is a bound under an assumption, not a score, but it is the honest way to put the two numbers side by side. The post also does not say which setting was run, zero-day or one-day, or how many attempts each task got. Two details matter for contamination: the benchmark's default setup leaves internet access on, with only a prompt asking the agent not to look up public exploits, and 15 of the 40 vulnerabilities have a public record that links to an exploit. There is no CVE-Bench leaderboard to compare against.

## HumanEval+

93.9% is 154 of the 164 problems. The EvalPlus leaderboard stopped at 2024 models, where the top entry is 89.0, so the number is plausible for a 2026 model and says little. These problems have been public since 2021, and HumanEval+ is a coding benchmark, not a security one.

## What the model is, and who can use it

OrcaRouter does not say what Zero 1.5 is built on. In a reply under the launch post it described the model as "not only abliterated, but post trained for cyber". The harness report says Zero 1.0 ran on a local vLLM server, which points to an open-weight base. At launch, OrcaRouter's one open security model, OrcaSAQ-2-Cyber-27B, was gated, and its Hugging Face metadata names Qwen3.8-27B as the base with a 262,144-token context, not the 1M on Zero 1.5's page. Neither the base nor what "updated weights" changed is disclosed anywhere I could find.

Access is gated: the page lists "an engagement, a passkey and the terms", and a reply describes KYC with a company email. OrcaRouter replied that the model is "for offensive red teaming". I found no system card, no model-specific use policy, no independent evaluation, and no named customer behind "has already helped protect some of the world's largest software companies". The demos in the thread run against deliberately vulnerable practice applications.

## What I would take from it

The CyberGym result is real and it is mostly a harness result: a cheap worker model on every task, the specialist on 43% of them, inside a benchmark whose own maintainers say the top is saturated. The Cybench and CVE-Bench numbers are self-reported on denominators the post does not explain, on public tasks that predate the model, with the settings that would make them comparable left out. None of that means the model is weak. It means that for a model sold specifically on finding real vulnerabilities, the launch gives no evidence that can be checked, and the one result that can be checked measures something else. For a security model the bar should be higher than for a chat model, not lower: a system card, the run settings, the excluded tasks, and an evaluation someone else ran.

## 18 October: OrcaCyber Nano 1.0, open weights

Eight days after this launch, OrcaRouter [released](https://x.com/OrcaRouter/status/2111871993532580058) a third model in the series, OrcaCyber Nano 1.0. It called it an "emergency release" and "the most capable local model in its under-16GB class": "27B parameters. 262K context. Vision. Fully offline." Unlike Zero 1.5, Nano has weights, on Hugging Face behind a click-through gate. I read the public card, the file listing and Hugging Face's metadata, and set them against the base model's open files.

<ModelCard repo="orcarouter/OrcaCyber-Nano-1.0" />

**What it is built on.** Asked in the replies whether Nano is based on Qwen 3.8 27B, OrcaRouter answered "Yes, post trained tho". The card gives the architecture as `Qwen3_5ForConditionalGeneration`, 64 layers at width 5120, 48 linear-attention and 16 full-attention, and 262,144 tokens of context: Qwen3.8-27B's config, line for line. The chat template in the repository's GGUF metadata is byte-identical to Qwen3.8-27B's `chat_template.jinja`, all 8,952 characters, down to its default reasoning effort of `xhigh` (measured). The vision projector is 927,606,848 bytes, which is Qwen3.8-27B's 460,730,096-parameter vision tower at two bytes a weight plus about 6 MB of headers (measured against the base's safetensors headers; the match is reasoned). The separate speculative drafter has 1,924,404,480 parameters, exactly the count of [z-lab's DFlash2 drafter](/articles/dflash2) for the same base (reported by Hugging Face for both). What I could not check is the main weights, tensor by tensor: those files are gated, and the unquantized `OrcaCyber-Nano-1.0-AI-Defense` repository the card names as its parent is not public. What post-training changed is not visible from outside.

**How 27B fits under 16 GB.** By quantization, not by being a smaller model. Qwen3.8-27B's language model, with its MTP head and without the vision tower, is 27,320,697,856 parameters (measured from the base's headers), 54.6 GB at BF16. Nano's two main files are 12,993,304,352 and 15,695,148,832 bytes, which is 3.80 and 4.60 bits per weight (reasoned). That is the lever OrcaSAQ-2 pulled, whose 12.27 GB checkpoint I [measured earlier](/articles/qwen3-8-27b-variants) at 3.59 bits per weight over the same parameter count, so OrcaRouter's reply that the two have a "very similar footprint" holds. The "significantly smaller" in the other reply is the quantization, which anyone can apply to the Apache-licensed base.

The three headline properties also do not hold at once. The card's own 16 GB recipe is the 13 GB file at 32K context with no image input. Every token of context costs the 16 full-attention layers 64 KiB of KV cache at 16-bit (4 KV heads of 256 dimensions, key and value, 2 bytes each), so 32K tokens add 2.1 GB and the full 262,144 add 17.2 GB (reasoned; the 48 linear-attention layers keep a fixed state of about 0.15 GB). Image input needs the 0.93 GB projector, which only the card's "24 GB+ card" recipe loads, and a reply under the post says it "Runs locally on a single 24GB GPU". Under 16 GB, 262K context and vision are each true of some configuration, but not of the same one.

**The benchmarks are general, and the base is missing.** AIME 2025, MATH-500, GSM8K, MBPP+ and IFEval measure maths, grade-school arithmetic, short Python functions and instruction following. None is a security benchmark, for a model "built for AI defense, vulnerability research, code security, and incident response"; the post says "Cyber-specific evals coming next", and the card says "Benchmark harness, settings and full result tables are being finalized." The scores decompose cleanly into 493 of 500, 1,286 of 1,319, 320 of 378 and 448 of 541 (reasoned from each benchmark's size). AIME 2025 has 30 problems and 96.23% is not a whole number of them, so it is an average over repeated samples, how many is not stated.

The table leaves out the one model that would show whether post-training did anything: Qwen3.8-27B. Qwen's own card reports none of these five benchmarks, so there is no published base number to put beside them. The single overlap is a reply: asked about coding, OrcaRouter said Nano "scores 90+% on LiveCodeBench" internally, and Qwen's card gives the base 90.3 on LiveCodeBench v6. On the published evidence the fine-tune cannot be told apart from the model it was made from.

**Licence.** The card's metadata says `license: other` with `license_name: qwen`. Qwen3.8-27B is Apache 2.0, which allows a fine-tune and a quantization under the publisher's own terms, provided the Apache licence and its notices travel with the files. The repository ships no licence file and the card's text names no terms, so what a user accepts at the gate is unclear, and the label does not match the base's licence (reasoned, not legal advice).

For a defender this is the more useful release: weights anyone can run offline and test. The missing test is the one that matters: one harness, Qwen3.8-27B against Nano, on security tasks.

## How I checked

I read the model page and its JSON card, the launch thread and its replies, and OrcaRouter's CyberGym harness report at commit `4847a00`, whose token and cost table I used for the split above. For each benchmark I read the paper and the repository (CVE-Bench at `9fb3e06`) and took the comparison rows from the public leaderboard data: CyberGym's `cybergym.json`, Cybench's `leaderboard.csv`, EvalPlus's `results.json`, and the CVE-Bench paper's Section 4.2. I did not call the model, run any benchmark, or run any security tooling. For the 18 October update I read Nano's public model card, its file listing and Hugging Face's metadata, and read Qwen3.8-27B's config, chat template, card and all 18 safetensors headers with range requests; Nano's own weights are gated and I did not download or run them. Not verified: which Cybench task was excluded, which CVE-Bench setting and attempts were used, the SWE-bench Pro V2 figure on the page, and OrcaRouter's statement that the agent made no answer lookups.
