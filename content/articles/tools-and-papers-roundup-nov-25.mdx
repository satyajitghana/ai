Two reposts from 23 November, and they meet in an odd place: both are about what a browser can draw now. One is a 2D renderer that has run on WebGPU everywhere except the web, finally running there. The other is a room you can walk through, built from 20 phone photos and a model that invents the rest.

For the first I read the repository at commit `fd1625e`, its benchmark write-up and the C++ that wraps Graphite, and weighed the npm package myself. For the second I read the posts and their replies and World Labs' Atlas docs, which describe a pipeline that matches what the post's tool shows.

## skia-wasm: Skia's GPU renderer on the page's own device

William Candillon maintains [React Native Skia](https://github.com/wcandillon/react-native-skia), which draws with Skia on iOS and Android. Its native builds can run Graphite, Skia's newer GPU backend, on Dawn, Google's WebGPU implementation. On the web it has used CanvasKit, Skia's older WebAssembly build: Ganesh on WebGL 2. Hence [the post](https://x.com/wcandillon/status/2124851075312460117): "Ironically enough, the only platform that couldn't run Skia on top of WebGPU was Web. Let's fix that."

[skia-wasm](https://github.com/wcandillon/skia-wasm) is the fix, MIT-licensed, first published to npm on 23 November and at 0.1.0 when I read it. It does not build Skia. `binaries.json` pins a 13,803,088-byte archive of prebuilt Graphite static libraries, by URL and SHA-256, from a `skia-wasm-m158` release of the React Native Skia repository, so the web and the phones run the same Skia revision. What the repository adds is the glue: Dawn's `emdawnwebgpu` headers and JavaScript library, which let Emscripten-compiled C++ talk to the browser's own `navigator.gpu`, and a thin API over plain C exports.

The shape of `src/cpp/context.cpp` says most of what matters. `Context::Init` takes the page's `WGPUDevice`, builds a Graphite `DawnBackendContext` around it and makes one recorder. The tick function is left null, with the comment "without Asyncify or JSPI nothing can wait on the GPU, so Graphite never blocks and work completes from the browser's event loop." That one choice keeps the module free of Emscripten's stack-unwinding machinery, and costs it synchronous readback: you cannot ask for pixels and get them on the same line. `Context::submit` is three Graphite calls, `snap()`, `insertRecording()` and `submit()`, and they come back in the benchmark below. Fonts come from bytes because there are no system fonts, CPU images must be uploaded as textures because Graphite only draws GPU images, and there are no pthreads.

Because the device is the page's, a Skia canvas can share textures with anything else on that device: a three.js scene, a compute pass, a video frame. That is the case the author makes in a reply: "Headless GPU rendering via node-dawn or in deno" and "Zero-copy interop with 3d libs, compute, media pipeline". He also calls it "mainly a fun experiment", and the README agrees: there is no stable API, and a minor version can break it.

The API looks like CanvasKit with the sharp edges filed off. `drawRect(x, y, width, height, paint)` takes numbers, not rect objects in wasm memory. Enumerations are strings that throw when misspelled, colours are CSS strings, every angle is in radians, and an object can be freed with `dispose()`, a `using` declaration, or left to a finalizer:

```ts
const sk = await Skia.init({ device })
const surface = sk.surface(canvas)
const glow = sk.paint({
  shader: sk.linearGradient({ start: [0, 0], end: [512, 0], colors: ["#f97316", "#ec4899"] }),
  maskFilter: sk.maskFilter.blur(8),
})

function tick() {
  const c = surface.getCanvas() // starts a frame
  c.clear("white")
  c.drawCircle(256, 400, 48, glow)
  surface.flush() // snap, insert, submit
  requestAnimationFrame(tick)
}
```

It covers paths with boolean ops, gradients, runtime effects, image and mask filters, paragraphs and PNG, JPEG and WebP encoding. Skottie, SVG documents, vertices and font fallback are not in it yet. The author's own note in the thread is that it "seems to work well on Safari and Firefox (wgpu)", Firefox's WebGPU being the Rust `wgpu` implementation, not Dawn.

### Where a frame goes

The repository's [BENCHMARK.md](https://github.com/wcandillon/skia-wasm/blob/main/BENCHMARK.md) is the best thing in it, because it reports a loss and finds the cause. It draws four synthetic scenes, every item animated every frame, with canvaskit-wasm 0.41.1 (the build React Native Skia uses on the web today) and with skia-wasm, on an M5 Max laptop and a Galaxy S25 Edge phone, and times the main thread. skia-wasm is 1.2x to 1.7x faster on the shader rectangles and the animated paths, and 2.1x to 2.8x slower on 10,000 rounded rectangles and 2,000 images.

The split on the phone shows where. Recording, the drawing calls themselves, is cheaper in skia-wasm on every scene: 9.74 ms against 10.00 ms for the rectangles, 0.38 ms against 1.32 ms for the paths. The deficit is entirely in submit: 17.8 ms for skia-wasm's snap, insert and submit against 0.28 ms for CanvasKit's flush on the rectangle scene. Counted on the laptop, that frame is 30,667 WebGPU calls against 4 WebGL calls; the image scene is 7,918 against 250. Ganesh batches those items into one instanced draw. This build of Graphite issues a `setBindGroup` and a `drawIndexed` per item, because Graphite's Dawn backend turns immediates and storage buffers off under Emscripten (`DawnCaps.cpp`). The author's note is that the phone already reports what a fix needs: a `maxImmediateSize` of 64, 16 storage buffers per stage, and `setImmediates`.

<FrameSplit />

On the laptop both libraries hold 60 frames a second on every scene, so for a few hundred shapes none of this shows. On the phone it does: the rectangle scene runs at 32 frames a second against CanvasKit's 60 when cool, and 18 against 46 once the phone has heated up and capped its cores. The write-up's measurement of that throttling is worth reading in its own right. Drawing the same scene repeatedly, the phone's fastest cores fell from 4.47 GHz to 1.96 GHz within 33 seconds while Android's thermal status still read 0, so the variant measured first in a page load ran on a phone 1.6 to 1.8 times faster than the ones after it. The runner now records the clock limit four times a second and only compares figures taken under the same limit. Most phone benchmarks I read do not do that.

The same document records an idea that did not survive. An earlier version had a retained API, a display list recorded once and animated by writing numbers into wasm memory, on the theory that a call from JavaScript into wasm per operation is expensive. It measured a call at about 2 nanoseconds through a plain C export and about 7 through embind, and the display list within 2% of one-call-at-a-time on three of the four scenes. So it was deleted, and the bindings became plain C exports with no embind.

One reply asked whether the wasm is smaller than CanvasKit's, and the thread has no answer, so I weighed both packages from npm. `skia-wasm-0.1.0`'s `skia-wasm.wasm` is 5,902,133 bytes, and 2,133,369 after `gzip -9`. canvaskit-wasm 0.41.1's full build, the one the benchmark used, is 8,080,104 bytes, or 3,240,363 gzipped; its default build is 7,159,342. So about a quarter smaller than the full CanvasKit, with fewer features (no Skottie, no SVG DOM).

### rust-skia, from the replies

A reply pointed the author at [rust-skia](https://github.com/rust-skia/rust-skia), safe Rust bindings to Skia's C++ API, which he called "very cool to see". It tracks the same Skia milestone, chrome/m158, and its README lists Vulkan, Metal, OpenGL and Direct3D backends, a `metal-window-graphite` example, a `wasm32-unknown-emscripten` target (its README shows only a WebGL option there), and rendering on a `wgpu` application's device as experimental. That last one is the Rust-side twin of what skia-wasm does on the page. It is what [fframes](/articles/fframes) rasters with, through `skia_safe`.

<RepoCard repo="rust-skia/rust-skia" />

I think skia-wasm is right about its bottleneck and honest about it, and I would not ship it yet. For a UI with a few hundred paths and gradients it is already faster than CanvasKit and lighter to download. For anything that draws thousands of small things a frame, it waits on a Graphite setting that someone at Skia, or the author, has to turn on for Emscripten. The zero-copy argument is the one that would make me switch: a Skia layer that composites into a WebGPU scene without a readback is something CanvasKit on WebGL cannot give you.

## An apartment from 20 photos, and a painted twin

[Ian Curtis (@XRarchitect)](https://x.com/XRarchitect/status/2124960145558188152) posted a Gaussian splat of his apartment that he can walk through, cutting between the real rooms and a stylised version with pastel, brush-stroked walls. His X bio lists design work at AMD and at World Labs, so read this as a demo from someone close to the tool, not an outside test.

His thread gives the recipe: "I started with 20 input images ... using the @theworldlabs viewfinder tool. Then generated 15 more views to fill out the missing spaces. To re-mask the space I had gpt image stylize the images and then re-imported them to generate the painted version." In a reply he puts the cost at "about 5k credits (5\$) each", and says it does not yet hold a steady frame rate on a Quest 3. The second clip in the thread is the tool itself.

World Labs' [Atlas documentation](https://docs.atlas.worldlabs.ai/build-a-scene) describes the same three steps as API tasks, and the video's interface matches them. The docs do not use the name Viewfinder, so that the Studio button runs these exact tasks is my inference, from the matching steps and the matching price.

1. **Pose.** `images2PosedRGBD` estimates a camera and a depth map for each photo. Photos of one real place submitted together share one world.
2. **Generate views.** `atlasGenerate` takes the posed frames as `contextFrames` and new `targetCameras`, and paints what each camera would see, with depth when `returnDepth` is set. The docs suggest 6 to 12 cameras around the subject, inside space the photos show as empty, in one request, so the model decides the unseen parts once for all of them. From a single image, they say, a camera can turn about half its field of view or move about a third of the typical depth and still mostly show what the photo showed. Beyond that, "Atlas invents what the view shows."
3. **Splat.** `posedImages2Splats` reconstructs Gaussians from the posed RGBD frames, then by default refines them by rendering new views, cleaning those up and training against them. A refined run is 5,000 credits (\$5 at 1,000 credits a dollar); a draft with `refine: false` is 500 and returns in about 30 seconds. It takes 2 to 512 frames for a refined run, on one of four camera grids (1280x720, 720x1280, 960x720 or 528x704), and recommends 8 to 16 views for a single room with about half of each image shared with its neighbours.

His 20 photos plus 15 generated views make 35 frames, which by my arithmetic lands in the docs' "33 to 512" row: up to 30 minutes for a refined run. The docs' worked example, a potter's studio from one photo and seven generated views, took 18 minutes and returned 2,000,000 splats.

The painted version is the step to think about. He restyled each frame with an image model and splatted the restyled set. The docs' best-practice page is blunt about what goes wrong when views disagree: a dining table drawn two ways in two generated views became "overlapping, ghosted surfaces", and a coffee table became two tables. A per-image restyle has nothing to keep one frame's brushstrokes consistent with the next frame's, yet his painted walk holds together. My guess is that the splat's refinement averages the disagreement into the soft, smeared look the style already has. He does not say whether he reused the original cameras and depth or posed the painted images afresh.

The idea came from [@smallfly](https://x.com/smallfly/status/2124640912072380849), who made a painterly version of a 3DGS capture of Coiffure Mile End, a hair salon in his neighbourhood, with Ailleurs, his own tool on the World Labs API, spatially aligned with the original so that the salon's mirror works as a portal between the two. The same docs list where splats come out badly: skies, foliage, large plain walls, windows, thin structures such as chair legs, and faces.

Two cautions. Every view Atlas generates is a guess at geometry nobody photographed, and the docs say so. For a stylised walk that is fine; Curtis himself calls the result a "digital cousin". For the reality capture I care about, where a splat ends up as measurements and a BIM model, an invented wall behind the sofa is a defect you cannot see. And the product name moved under this post: World Labs' Marble docs now say Marble and its World API [will be discontinued on 8 January 2027](https://docs.worldlabs.ai/discontinuation.md), with Atlas as a separate product with its own accounts and keys. The camera-path app this site [took apart in October](/articles/marble-camera-studio) already ran on Atlas tasks.
