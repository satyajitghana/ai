A video went round this week of someone playing Grand Theft Auto V in Chrome on an M3 Pro, at `playgta5.com`. The replies split three ways: it is cloud gaming, it is an Xbox 360 emulator, or it cannot be real.

It is real, and it is none of the first two. I opened the site, downloaded every file it serves, read them, and ran the game headless on a 16-core server with no GPU. This is what is actually in the tab.

| | |
|---|---|
| What runs | Rockstar's RAGE engine and GTA V's game code, compiled to WebAssembly (wasm64, threads) |
| Engine binary | `game.wasm`, 63,201,802 bytes; about 91,000 functions, all still named |
| Graphics | Direct3D 11 calls recorded into a 32 MB ring, replayed on WebGPU by a worker |
| Shaders | 4,919 DXBC shaders translated offline to WGSL; 4,808 usable |
| Game data | 5,814 files, 20.9 GB, of which 1,528 `.rpf` archives are 20.3 GB; streamed, never downloaded whole |
| Storage | HTTP Range requests into an append-only store in the Origin Private File System |
| My run (measured) | world on screen at 188 s, 743 MB of game data, 0.3 fps on SwiftShader, 2,736 draws per frame |

One caveat before the engineering, because it shapes everything else: the binary was built from GTA V's own C++ source, and the 20.9 GB the site serves is Rockstar's game data. Neither is licensed for this. I come back to where the source came from near the end.

## What happens when you open the tab

The page is small and heavily commented. Its own description of itself is the best map there is, so I quote it where it matters.

It opens on GTA V's loading screen: the beach, the character art, the logo, sliding in on a tilted 3D plane. This is not a video. It is the game's Scaleform loading movie, `LOADINGSCREEN_STARTUP`, decompiled from its ActionScript and rebuilt in HTML and CSS with the same 55-degree camera, the same six random orders of 17 screens, the same 14-second cadence. The page says so in a comment, down to the font (`$Font2 = Chalet London 1960`).

Under it, a progress bar is fed by the engine's own log lines. A menu offers **Story Mode** (continue the newest savegame, or the Prologue with `?newgame=1`), **Sandbox Mode on the GTA V map** (free roam at a random spot with every weapon), and **Sandbox Mode on a map the page labels "GTA VI Map"**. That last one is `env_test` in the data. The choice can change until the engine reads its `-level` argument, about 62% into the load; until then the engine waits.

## It is the real engine, not an emulator

An emulator would ship a console's CPU interpreter and a disc image. Cloud gaming would ship a video decoder and a WebRTC connection. This site ships neither. It ships a 63 MB WebAssembly module and a manifest of game files.

I parsed the module's sections without running it:

| Section | Size |
|---|---|
| code | 48.2 MB |
| data | 7.8 MB |
| `name` (function names) | 6.8 MB |
| functions defined | 91,026 |
| imports | 86 |

The `name` section is the giveaway. It was left in, and it lists 91,111 function names. 41,286 of them contain `rage::`, the namespace of Rockstar's RAGE engine. The rest read like a tour of the game: 1,865 handlers in `network_commands`, 1,606 in `vehicle_commands`, 1,392 in `ped_commands`, 1,162 in `hud_commands`. Those are the native functions GTA V's mission scripts call.

The strings agree. Assertion messages carry the build machine's source paths, for example `E:/P1/GTA5/SRC/DEV_NG\RAGE\BASE\SRC\net/status.h`. `DEV_NG` is the next-gen branch, the one the PC version came from.

Two things follow from this. The port was built **from C++ source**, by a compiler, not by translating machine code. And the source was a development build: the engine starts a thread called `BugstarAssertLogging` (Bugstar is Rockstar's internal bug tracker), the page notes that "this build has debug key bindings", and it passes `-fastscriptcore` because without it the script interpreter runs its debugging core, which "looks up two breakpoint tables for every script instruction".

The memory is the other tell. The module imports one memory with flags `0x7`: it has a maximum, it is shared between threads, and it is **64-bit**. Minimum 49,152 pages, maximum 262,144; at 64 KB a page that is a 3 GB starting heap and a 16 GB ceiling. Classic 32-bit WebAssembly stops at 4 GB, and a 2013 PC game sized for 8 GB machines does not fit in that. In my run, once the world was up, the engine reported a 2,444 MB malloc arena with 2,405 MB of it in use.

## Why the engine runs in a worker

A game engine assumes it owns its threads. It blocks on mutexes, sleeps, spins and waits for the GPU. A browser's main thread may do none of that. So the page does almost nothing:

- It transfers the canvas to an `OffscreenCanvas` and hands it to `loader.js`, a dedicated worker.
- `loader.js` becomes the engine's "main thread". Static constructors and `main()` run there, and the game loop blocks it for good, which is fine because nothing else lives on it.
- Every engine thread is an Emscripten pthread, which is a Web Worker running the same `game.js` glue against the same shared memory. In my run 75 of them started.

The engine sizes its worker pools from the core count, so a phone that reports eight cores gets dozens of 20 MB workers. The page's low-memory profile (devices reporting 4 GB or less) lies about the core count: it tells the engine there are 2 cores, which the page says gives 54 threads instead of 80 to 116. It also skips whole groups of threads the browser cannot use. My log lists 18 skipped: the hang-detect watchdog, Bink video, the TCP and `netThrPool` network workers, `HttpQuery`, Bugstar logging and nine replay-recording threads. The command line adds `-nonetwork -noSocialClub`.

The rule that makes the rest work: **engine threads never call a browser API that has to yield**. `fetch`, WebGPU and audio are all asynchronous, and a C++ thread blocked in `Atomics.wait` never returns to an event loop to receive their callbacks. So three JavaScript workers with normal event loops do the asynchronous work, and the engine talks to them only through shared memory.

The map above is the whole architecture. The prose version: the page writes keys and mouse deltas into a 256-byte key table plus a few int32 words, with `Atomics.store`. The engine writes Direct3D commands into a ring that the GPU worker drains. It posts file reads into slots that the IO worker serves. It mixes audio into a ring that an `AudioWorklet` plays. Each worker is the only owner of its browser API, and each handoff is a word in shared memory flipped atomically.

## Graphics: Direct3D 11, replayed on WebGPU

The engine was not rewritten to use WebGPU. It still creates a Direct3D 11 device. In this build that device is fake. The function names show a namespace called `wasm_null_d3d`, with classes like `NullDevice`, `NullContext`, `NullSwapChain` and `NullResource`, implementing D3D11's COM interfaces. Each call becomes an opcode plus payload words in a 32 MB ring in shared memory (`[wgpu] start: ring … size 33554432` in the log).

`wgpu_worker.js` is the other end. Its header explains the split better than I can:

- "WebGPU objects cannot cross threads, but D3D11 resources are created by any engine thread (streaming, main, render)." So the game threads only emit commands, and every WebGPU object lives in the worker.
- "WebGPU is asynchronous… the game's blocking C++ threads never have to yield to JS. They wait on a futex/fence word in the ring when they need a result (readback, occlusion query)."

The interesting part of a translation layer is never the happy path. It is where the two APIs disagree. The worker's comments list the mismatches it has to paper over:

- **Constant buffers.** D3D11 shaders use up to 7 constant buffers per stage. WebGPU allows 10 dynamic-offset uniform bindings per pipeline layout, across all stages. So every stage's constant buffers are merged into one struct at binding 0, copied per draw into a uniform ring, and bound with one dynamic offset. The copies go into a JavaScript mirror first: one `queue.writeBuffer` per draw "was ~10% of the worker's time at 1,700 draws per frame".
- **Depth read as colour.** D3D11 lets a shader `Load` a depth texture as if it were a float texture. WebGPU only binds it as `depth`. The worker keeps an `r32float` proxy of each such depth texture and refreshes it with a render pass whenever the depth was drawn into.
- **Alpha-to-coverage.** The foliage shaders rely on D3D's alpha-to-coverage on single-sample targets instead of `clip()`. WebGPU only honours the flag with MSAA, so the worker compiles a variant with an explicit alpha test.
- **Inter-stage limits.** Some GPUs (the comment names a Chromebook's Intel GPU) allow only 16 inter-stage variables, and Dawn's Vulkan backend counts clip distances against them. Shaders for cables, particles, clouds and vehicle parts wrote location 15 next to a clip distance and failed. The worker renumbers those outputs.
- **Base vertex.** D3D's `SV_VertexID` excludes the draw's base vertex; WebGPU's `vertex_index` includes it. The worker folds the offset into the vertex buffer binding, but only for the shaders that read the IDs: 6 read the vertex ID and 93 the instance ID, of about 4,800.

### The shaders

Rockstar ships compiled DXBC bytecode, not HLSL source. The port translated every shader offline to WGSL and serves them from `shaders/index.json`, keyed by a hash of the DXBC, bundled into packs so a browser makes about 20 requests instead of about 6,000. I counted the index:

| Stage | Shaders | Translated |
|---|---|---|
| pixel | 3,667 | 3,667 |
| vertex | 1,112 | 1,112 |
| compute | 31 | 29 |
| domain | 71 | 0 |
| geometry | 20 | 0 |
| hull | 18 | 0 |
| **total** | **4,919** | **4,808** |

That is 72 MB of WGSL in 18 packs, about 4 MB each. The zeros are not failures of effort. WebGPU has no geometry, hull or domain stage. The 109 shaders in those stages are tessellation and the geometry-shader paths of instanced shadows (`GS_ShadowInstPassThrough` in the cloth effects, for example), so those effects have to fall back to the engine's non-tessellated paths or go without.

### Pipelines without hitches

The last problem is one every WebGPU port hits. A render pipeline compiles on first use, and a synchronous compile makes everything behind it wait tens of milliseconds. A new street streaming in means hundreds of new pipelines. The worker compiles them asynchronously and **skips the draws** that need one until it is ready. On a slow machine that showed as white holes: "28,000 draws skipped in one second" on a 4-core Chromebook.

The fix is to know the pipelines in advance. Every pipeline is also keyed by a recipe (shader hashes, input layout, blend, depth and raster state words, target formats). The site ships a seed of 720 recipes recorded from headless runs. Each browser adds its own to IndexedDB, and while the game loads, recipes whose shaders have arrived are compiled ahead. My run's log line: "title screen held 19.3 s for compiling pipelines… compiled ahead 719, used 159, compiled when first drawn 37". 

## Storage: 20.9 GB you never download

The manifest lists 5,814 files and 20,944 MB. Almost all of it, 20,304 MB, is 1,528 `.rpf` archives, RAGE's package format. The biggest single file is the player character models at 532 MB. `x64/levels` alone is 14.2 GB.

Nobody downloads that into a tab. The engine's file layer was redirected (`httpfs_wasm.cpp`) so that a read becomes a request: an engine thread fills a 16-word slot in shared memory (file id, 64-bit offset, destination address, length, state), rings a doorbell word, and waits. The IO worker serves it.

The comments record how the IO worker got to its current design, and the dead ends are the useful part:

1. **Synchronous XHR from each engine thread**, behind a service worker that cached blocks. Each response is a fresh `ArrayBuffer` that is only freed when that worker's garbage collector runs, and a worker that lives inside wasm or in `Atomics.wait` almost never runs it. The bytes piled up as "~1.5 GB of renderer memory", with the service worker adding "another ~0.9 GB".
2. **256 KB blocks, then 16 KB blocks with read-ahead.** At boot the engine mounts about 1,200 archives and reads only each one's table of contents: median 3 KB, 4.9 MB for all of them. Big blocks made "the boot download 25x larger for those files".
3. **Now:** 4 KB blocks, streamed chunk by chunk into an append-only `store.bin` in the Origin Private File System through a synchronous access handle, with a `journal.bin` of 16-byte entries mapping (file, block) to an offset, and copies straight from the store into the wasm heap. No JavaScript buffers to collect. Read-ahead only follows large sequential reads.

Two further tricks cut the wait:

- **A recorded boot set.** The engine reads nearly the same bytes on every boot. A run with `?record=1` logged them, and every visit now prefetches that list at once, in parallel with downloading the engine. I measured the list: 2,918 file ranges, 582 MB (509 MB for the low-memory profile).
- **Hints from the streamer.** RAGE's streaming system queues reads and performs them one at a time on one thread. The port makes it announce queued reads in a ring, and the IO worker fetches up to 96 of them ahead, so a demand read usually finds its blocks already stored or in flight.

Why so many requests in flight? Because the host answers a Range request at a few hundred KB/s per stream, whatever the visitor's link. The porter measured it, and throughput tracked the number of streams, not bandwidth:

At 128 in flight that is 14.1 MB/s, and the boot set takes about 41 s; at 6 it is 3.4 MB/s and nearly three minutes. That is why the boot set runs in 32 lanes and why your fibre connection does not make the first load much faster (reported numbers, my arithmetic). The whole manifest at the best rate would be about 25 minutes. The engine never needs it: in my run the world was up after 743 MB.

The second visit is different. The store survives in OPFS, keyed to the manifest version, and blocks already there cost nothing. Savegames are separate: they live in IndexedDB (`gta5-userdata`), because the OPFS store is exclusive to one tab and is thrown away when the game data changes.

## Input, audio and a 1 ms timer

The smaller pieces are worth a paragraph each, because each is a place where browser behaviour leaks into a game that never expected a browser.

**Input** is a block in shared memory: 256 key bytes indexed by Windows virtual-key codes, then int32 words for mouse position, deltas, wheel, buttons, focus and pointer lock, then a 64-entry text ring. The page maps DOM key codes to Windows VK codes. It also aliases `I/K/J/L/U/O` to the numpad keys that GTA uses for aircraft pitch and roll, because most laptops have no numpad.

**Audio** is a ring of interleaved float stereo that the engine's mixer writes and an `AudioWorklet` reads, 128 frames per callback, at 48 kHz. It cannot start until the first click or key press.

**Timers** were the strangest bug. Chrome on Windows rounds every wait with a timeout up to the OS timer tick, 15.6 ms, unless the renderer has a timer under 16 ms pending. The engine's sleeps, its 1 ms event waits and its frame limiter all use `Atomics.wait` with timeouts. Measured by the porter: "a 1 ms wait takes 15.5 ms; with this timer 2.1 ms", and the limiter held a 60 fps cap to 37 fps. The fix is one line on the page, an empty `setInterval(() => {}, 1)`, which exists only to keep Windows on a fine tick.

## What it costs

The site is honest in its own comments about where it struggles, and three numbers stand out.

- **Memory.** Every engine thread is a Web Worker of about 20 MB. The heap starts at 3 GB. The low-memory profile (devices reporting 4 GB or less) quarters texture memory, drops variety, density and LOD to minimum and turns shadows off; measured by the porter, GPU memory went from 1.16 GB to 0.5 GB and streamed assets from 1.38 GB to 0.95 GB. When a tab still runs out, it dies with "Aw, Snap!" and cannot say why, so the page runs a watchdog that says "the device may be out of memory" after 30 s of silence.
- **Draw calls.** Every WebGPU call costs "a few microseconds of validation + serialisation", and the worker spends much of its code avoiding them: a pipeline memo keyed by small integers instead of strings, bind groups cached by resource id, constants packed once per frame. The shadow cascade pass alone was 600 to 900 of 1,300 to 2,900 draws per frame, and a 4-core Chromebook spent about 110 µs per draw. That is why the low profile turns shadows off.
- **The host.** Comments dated 6 October say 10,000 visitors in a day produced thousands of error responses (503, 500, 429), and "the engine quits when a data file cannot be read". Every fetch now retries up to 8 times with jittered backoff over about 20 s.

## Where the source came from

The site does not say, and I cannot prove it. What I can show is what the binary needs: a full C++ source tree for RAGE and GTA V, on Rockstar's own build paths, in a development configuration. Rockstar has never published that source. The [reVC](https://github.com/Lolendor/reVCDOS) Vice City browser port that circulated earlier this year is different in kind: its engine is reVC, a community reverse-engineering of the original, not Rockstar's source.

GTA V's source did leak. A partial dump surfaced around Christmas 2023, and in September a roughly 200 GB archive from the 2022 Rockstar breach, described as "GTA V source code, debug builds from every platform" plus early GTA 6 development material, began circulating ([gtaboom](https://www.gtaboom.com/a-massive-gta-5-source-code-leak-with-early-gta-6-assets-is-circulating-online-f461), reported). A development tree with `env_test` levels and a Bugstar thread is consistent with that archive. The "GTA VI Map" label on the menu is the site's, not Rockstar's, and I would not read more into it than that `env_test` is a test level from Rockstar's tree.

Serving 20.9 GB of Rockstar's game data and a binary compiled from leaked source to 10,000 people a day is not a gray area. I would expect the site to be gone soon. I have not linked it, and nothing here tells you how to get the data.

## What I take from it

Strip away the provenance and this is a clean demonstration of something that was not true two years ago. The browser now has every primitive a 2013 AAA engine needs, without rewriting the engine:

- 64-bit WebAssembly with shared memory, so a 3 GB heap and 75 real threads;
- `Atomics.wait` in workers, so C++ can block the way it always did;
- WebGPU, close enough to D3D11 that a recorder and a replayer bridge them, with the gaps (tessellation, geometry shaders) known and listed;
- synchronous access handles in OPFS, so a 20.9 GB file system can be faked one 4 KB block at a time;
- `AudioWorklet` and `OffscreenCanvas` for the rest.

What did not translate is equally clear: no geometry or tessellation stages, a per-call cost that makes thousands of draws expensive, garbage collection that never runs in a busy worker, timers that round to the OS tick, and a host that has to serve streams, not files. Each of those has a comment in the source explaining the workaround. If you ever port a native engine to the web legitimately, those comments are a better checklist than most documentation.
