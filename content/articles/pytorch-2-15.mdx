PyTorch 2.15 came out on 28 October. The [release blog](https://pytorch.org/blog/pytorch-2-15-release-blog/) counts 3,117 commits from 583 contributors, and its first item is the one that changes jobs people already run: every process group created with `backend="nccl"` now gets a rewritten NCCL implementation. The blog gives that change three short paragraphs. The [full release notes](https://github.com/pytorch/pytorch/releases/tag/v2.15.0) give it a page, and the pull requests behind it give the rest, including a bug report from vLLM that shows what the switch costs.

The first version of this article read only the blog and called the NCCL change untestable. That was half right. The NCCL path needs NVIDIA GPUs, but the reconfiguration contract it implements is shared with gloo, which runs on a laptop. So this rewrite does three jobs: it explains what a communicator is and why building it eagerly matters, it walks one group through a rank failure on four real CPU processes, and it times the release's Apple Silicon numbers on an M1 Max, the one set of claims this machine can check directly.

## A process group is a list of names; a communicator is the wiring

Distributed training starts with N processes, usually one per GPU, that need to agree on numbers. Each has a **rank** from 0 to N−1. To sum gradients across all of them you call `dist.all_reduce(tensor)`, and every rank gets the same total back.

A **process group** is PyTorch's object for "these ranks, talking together". `init_process_group` makes the default one with every rank in it, and `new_group` makes subsets: a tensor-parallel group of 8, a data-parallel group of 64, a pipeline pair. Large jobs make dozens. The group itself is cheap. It holds the member list, a key-value **store** (usually a TCP server on rank 0) that members use to find each other, and a pointer to a **backend** that does the actual moving of bytes.

For NVIDIA GPUs the backend is NCCL, and the thing NCCL builds is a **communicator** (`ncclComm_t`). A communicator is the expensive part. To make one, rank 0 creates a unique id, publishes it through the store, and every member calls `ncclCommInitRankConfig` with it. That call is itself collective: all members must show up. NCCL then discovers the topology (NVLink, PCIe, InfiniBand), picks ring and tree layouts, opens connections to peers and allocates GPU buffers for staging data in flight. The buffers are the part that shows up in `nvidia-smi`.

Since all members must join, when you build the communicator is a design choice with consequences:

- **Lazy** (the legacy `ProcessGroupNCCL`): build it at the first collective that needs it. A group you create and never use costs nothing. A misconfigured network shows up at the first `all_reduce`, which may be minutes into the job.
- **Eager** (the new default): build it inside `init_process_group` or `new_group`. Errors surface at startup, and the first collective is not slowed by a bootstrap. But every group pays for its buffers immediately, used or not.

Write $G$ for the groups a process creates, $U$ for the ones that ever run a collective, $c_0$ for what a communicator allocates when it is built, and $c_1$ for its footprint after it has run. Then, per GPU,

$$
M_{\text{lazy}} = U\,c_1, \qquad M_{\text{eager}} = G\,c_0 + U\,(c_1 - c_0).
$$

The two agree once every group is used ($U = G$). They differ by $(G - U)\,c_0$ when some groups are made "just in case", which serving engines do all the time.

## What `backend="nccl"` resolves to now

None of the four backend names is new. I installed `torch==2.14.1` and `torch==2.15.0` from PyPI side by side and read both wheels: `nccl`, `nccl2`, `nccl-lazy` and `nccl-legacy` are registered as entry points in both. What changed is one comparison in `_register_builtin_nccl_backend`. In 2.14.1 plain `nccl` builds the rewrite only if `TORCH_DIST_USE_NCCL2 == "1"`. In 2.15.0 it builds the rewrite unless the variable is `"0"`. Registration happens the first time a process asks for that name, so the variable has to be set on every rank before the first group is created.

<BackendSwitch />

The rewrite was ported from [torchcomms](https://github.com/meta-pytorch/torchcomms), Meta's experimental communications library, whose README now says it is deprecated because its features have been upstreamed into `torch.distributed`. The [release notes](https://github.com/pytorch/pytorch/releases/tag/v2.15.0) list what differs from the legacy backend in practice:

- Communicators are created eagerly in `init_process_group()` and `new_group()`, "allocating GPU memory even for unused groups".
- Each group binds to one GPU: `device_id` if you pass it, else `LOCAL_RANK % torch.cuda.device_count()`. `torch.cuda.set_device()` is ignored, and one process driving several GPUs needs `nccl-legacy`.
- `isinstance(pg, ProcessGroupNCCL)` is now `False`, and legacy-only methods such as `comm_split_count()` are gone.
- An async `all_gather`'s future holds the list of per-rank outputs rather than one stacked tensor.
- `nccl-legacy` and `TORCH_DIST_USE_NCCL2=0` "will be removed in the next release".

The legacy behaviour is on a one-release clock. The two supported choices are `nccl`, which is eager, and `nccl-lazy`, which builds one eager communicator for collectives and a separate lazily created two-rank communicator and stream for each send/recv peer pair, so point-to-point traffic to different peers can overlap. [PR #193241](https://github.com/pytorch/pytorch/pull/193241) makes pipeline stages print a warning steering users to `nccl-lazy`, because pipeline parallelism is mostly point-to-point.

The PR that flipped the default ([#192281](https://github.com/pytorch/pytorch/pull/192281)) carries a TorchTitan test matrix: ten training steps with the legacy and new backends gave identical loss and gradient norm, and eight parallelism layouts passed on 4 GPUs.

## What eager creation costs

The release notes say each eagerly created communicator allocates about 200 MiB. The clearest measurement is in [issue #199957](https://github.com/pytorch/pytorch/issues/199957), whose report says the switch broke vLLM's nightly CI with out-of-memory errors on H100s. vLLM's tensor-parallel-2 setup creates about ten groups (world, TP, PP, DP, EP and others, several with one rank), and the engine saw about 2.5 GiB less free memory per GPU with the new backend.

<Figure src="/articles/pytorch-2-15/fig3.png" alt="The issue text and its results table. On torch 2.15.0.dev20261002 with NCCL 2.30.7 on two H100 96GB GPUs and 9 groups: nccl2 default allocates +2080 MiB (231 MiB per group) after nine new_group calls and +4672 MiB after one all_reduce per group; legacy allocates +0 MiB then +4672 MiB; nccl2 with NCCL_COMM_SPLIT_SHARE_RESOURCES=1 allocates +1188 MiB (132 MiB per group) at both points." caption="Eager creation charges every group up front; the totals converge once all groups are used (pytorch/pytorch issue #199957, Results)." />

That table is the formula above with numbers in it: $c_0 \approx 231$ MiB and $c_1 \approx 519$ MiB per group on that machine (2080 and 4672 divided by 9). A follow-up in the same thread on GB200 measured 197 MiB per group. One mechanism detail explains the second option. On the new backend, `new_group` normally builds a group by splitting the parent's communicator (`ncclCommSplit`) rather than bootstrapping from nothing, so an NCCL setting that lets split communicators share their parent's resources applies to every subgroup. There are three ways out, and they trade differently. `nccl-legacy` works today and disappears next release. `NCCL_COMM_SPLIT_SHARE_RESOURCES=1` lets split communicators share buffers, which cut the issue's total to 1188 MiB whether or not the groups were used, at a possible cost to concurrency the reporter flagged as unmeasured. And 2.15 shipped a third, `ProcessGroupNCCL.Options.lazy_init` from [PR #200020](https://github.com/pytorch/pytorch/pull/200020), which keeps the new backend but builds a group's communicator on its first operation. Its PR reports nine groups going from +1774 MiB to +0 MiB at `new_group`, with nothing changed after use. The issue is still open as I write, and the default stays eager.

## Reconfiguration: losing a rank without losing the job

The second half of the headline is reconfiguration. In a classic job, one dead GPU kills everything: the survivors block in their next collective until a timeout, the launcher tears the job down, and it restarts from the last checkpoint. On thousands of GPUs that is a routine event, and the lost time adds up.

Reconfiguration keeps the surviving processes alive and rebuilds the communicator with a new member list. The API in 2.15 is three experimental functions in `torch.distributed`, documented under "Fault-tolerant reconfiguration":

- `_supports_reconfigure(group)` says whether the backend can do it.
- `_get_reconfigure_handle(group)` returns a short string identifying this process in the current generation, for example `gloo:1:-1:1:127.0.0.1:29641` (backend, rank, generation uuid, stable rank, store address).
- `_reconfigure(uuid, handles)` builds a new generation. You pass a fresh `uuid` every time and one handle per member; a handle's position in the list becomes that process's new rank.

PyTorch does not decide who is alive or tell the survivors. Something outside the group, a fault-tolerance controller such as torchft or your own rendezvous over the store, collects handles from the processes that are still answering and hands every one of them the same list.

For NCCL, a full reconfigure tears the old communicator down and runs a fresh `ncclCommInitRankConfig` on everyone, which is the same bootstrap as at startup. 2.15 adds an opt-in fast path ([PR #199240](https://github.com/pytorch/pytorch/pull/199240)), ported from torchcomms: with `TORCH_NCCL2_RECONFIGURE_SHRINK_GROW=1` on every rank and NCCL 2.29 or newer, survivors keep their existing communicator and call `ncclCommShrink(NCCL_SHRINK_ABORT)` to cut the dead ranks out, and newcomers are added with `ncclCommGrow`. I checked the shipped v2.15.0 source (`nccl2/ReconfigureNCCL.cpp`) rather than trusting the PR text. The rule that decides the path depends only on the handle list, so every rank picks the same one:

1. The **quorum** is the largest set of handles that share a previous generation uuid, and it needs at least two members.
2. The quorum must come first in the list, in ascending old-rank order, because NCCL's shrink keeps survivors in order and grow appends joiners at the end. Any other order means a fresh init on every rank.
3. A reconfigure with the same members and no joiners also uses fresh init, since the old communicator may already be revoked.

Reconfigure needs `ncclCommRevoke`, which the source gates at NCCL 2.28 for CUDA builds and RCCL 2.30.7 for ROCm ([PR #194774](https://github.com/pytorch/pytorch/pull/194774), which explains that RCCL 2.30.4 hangs on the missing-rank path). The Linux CUDA wheel on PyPI depends on `nvidia-nccl-cu13==2.30.7`, so the default install clears both NCCL floors.

### The same lifecycle, run on four CPU processes

The reconfigure contract is the same across backends; the NCCL source says its handle format and rank-assignment rule "match ProcessGroupGloo's reconfigure". Gloo runs on CPU, so I could drive it. Four processes started a group with `enable_reconfigure=True`, three of them formed generation 1, one died, the survivors shrank to generation 2, and the spare joined in generation 3. This is the core of the script:

```python
dist.init_process_group("gloo", store=store, rank=wid, world_size=4,
                        enable_reconfigure=True, timeout=timedelta(seconds=5))

def gather_handles(store, tag, me, members):
    store.set(f"{tag}/{me}", dist._get_reconfigure_handle())
    return [store.get(f"{tag}/{m}").decode() for m in members]

h = gather_handles(store, "gen1", wid, [0, 1, 2])          # process 3 waits
dist._reconfigure(uuid=1, handles=h).wait()
x = torch.tensor([float(wid + 1)]); dist.all_reduce(x)     # 1 + 2 + 3
# process 2 calls os._exit(0); the others try one more all_reduce, which times out
h = gather_handles(store, "gen2", wid, [0, 1])
dist._reconfigure(uuid=2, handles=h).wait()                # 1 + 2
h = gather_handles(store, "gen3", wid, [0, 1, 3])          # process 3 joins as rank 2
dist._reconfigure(uuid=3, handles=h).wait()                # 1 + 2 + 4
```

And what it printed on 2.15.0 (2.14.1 printed the same):

```text
[rank0] gen1 rank 0 size 3 all_reduce 6.0
[rank2] exiting (simulated failure)
[rank0] collective with dead peer failed after 5.0 s: RuntimeError ... Timed out waiting 5000ms
[rank0] gen2 (shrunk) rank 0 size 2 all_reduce 3.0
[rank3] gen3 (grown) rank 2 size 3 all_reduce 7.0
exit codes [0, 0, 0, 0]
```

My first attempt also hung, which is instructive. I had the survivors fire an asynchronous `all_reduce` at the dead peer and abandon it after a 3-second `wait`. The wait raised, the survivors went on to shrink, grow and print the right sums, and then neither of them exited: the launcher's 90-second `join` gave up on both with no error printed. The group's default timeout is 30 minutes (`default_pg_timeout` in the wheel), and my reading is that the abandoned operation was still holding the group until then. I changed both the call and the timeout at once, a blocking `all_reduce` instead of the abandoned one and a 5-second group timeout, so the transport itself failed the collective; after that every process exited with code 0. That is the shape of a real distributed hang: the rank that is stuck is not the one that failed, and nothing is printed.

### The flight recorder, and why it gated the rollout

That is why the debugging half of the headline exists. The legacy backend records every collective in a ring buffer (the flight recorder) and can dump it when the watchdog sees a timeout. The rewrite had none. [PR #192233](https://github.com/pytorch/pytorch/pull/192233) says that before it, the new backend "produced nothing at all when it hung, which was the operability regression blocking its rollout". It adds a backend-agnostic recorder fed from the c10d dispatcher hooks, so it also covers MPI and UCC. [PR #199092](https://github.com/pytorch/pytorch/pull/199092) publishes watchdog health to the debug server, so one rank's timeout triggers a dump on every rank. And [PR #192858](https://github.com/pytorch/pytorch/pull/192858) fixed a bug that would have attached no recorder at all to the default name once the default flipped, because one code path read the environment variable and another assumed plain `nccl` recorded itself.

Other fallout fixed before the release, which tells you what to test in your own stack: vLLM's probe for the communicator pointer called the legacy `_comm_ptr()` and broke ([#198865](https://github.com/pytorch/pytorch/pull/198865)), and the watchdog thread created a stray CUDA context on GPU 0 from every rank on the host, seven extra 522 MiB contexts per host on a 256-GPU TorchTitan run ([#198339](https://github.com/pytorch/pytorch/pull/198339)).

## The rest of the breaking-changes list

The blog lists five backwards-incompatible changes. The release notes list 26, plus 8 deprecations, and the first version of this article repeated the blog's count. The ones most likely to bite, beyond NCCL:

- **Distributed checkpoints are not readable by older versions.** Metadata now records tensor strides, and 2.14 fails on a 2.15 checkpoint with `too many values to unpack (expected 5)`. There is no flag to write the old format. Upgrade every reader before any writer.
- **FSDP2 gradient dtype.** With `MixedPrecisionPolicy(param_dtype=torch.bfloat16)` and `reduce_dtype` left at `None`, fp32 parameters now accumulate and reduce-scatter gradients in fp32, which the notes say doubles reduce-scatter bytes. Set `reduce_dtype` explicitly to keep 2.14 behaviour.
- **Pipeline config renamed without an alias.** `pipeline_per_direction_p2p` is now `pipeline_per_edge_p2p`; setting the old attribute raises, and the old environment variable is silently ignored.
- **Wheels.** Python 3.10 is gone; the PyPI tags go from `cp310`–`cp314` in 2.14.1 to `cp311`–`cp315` in 2.15.0. CUDA 12.6 and 13.0 wheels are no longer published, and the default is CUDA 13.2. MPS now requires macOS 15.
- **Checkpoint loading is stricter.** A security fix means that after `import torch.distributed`, `torch.load(weights_only=True)` no longer treats builtin exceptions as safe globals, so checkpoints that pickled an exception need `torch.serialization.add_safe_globals`.
- **Small semantic shifts.** `import torch` cannot be re-run in one process; nested tensors are no longer allowed by `torch.load(weights_only=True)`; selective activation checkpointing saves rather than recomputes ops with ordered effects; ops undefined for complex inputs raise `TypeError`; float32 `sin` and `cos` on Arm CPUs use 3.5-ULP kernels (faster, less accurate).

## Everything else the release names

The blog's fifteen feature sections cite 108 PR numbers between them, about 3.5% of the 3,117 commits, so the blog is a selection, and it spends its words on distributed work and Apple Silicon.

<ChangeMap />

**One-sided transports.** `torch.distributed._transport` moves data by one side reading or writing the other's memory, with no matching receive and no process group, connecting peers through a store. NIXL is the first backend, and `read_stream`/`write_stream` enqueue transfers on a CUDA stream so they can be captured in a CUDA graph. This is the primitive for pushing a KV cache from a prefill machine to a decode machine. The `_transport` directory is in the 2.15.0 wheel and not in 2.14.1, and the leading underscore means what it usually does.

**FSDP2 and pipelining.** `param_dtype_override_fn` keeps chosen parameters, the blog names MoE router gates and norms, in fp32 while the rest trains in bf16, with one all-gather per `fully_shard`. Before, that meant splitting the module into separate FSDP units and paying for extra all-gathers. `finalize_backward(async_op=True)` lets gradient reduction overlap other compute, and pipelines allocate receive buffers just before each receive.

**NVGEMM for NVFP4 decode.** The CuTeDSL GEMM backend folds the NVFP4 dequantization scale into the GEMM, removing one pointwise launch per layer during decode on Blackwell. The blog gives no number for this, and I have no Blackwell GPU.

**Platforms.** FlyDSL GEMM templates on AMD gfx950 (ten `flydsl` files under `torch/_inductor` in 2.15.0, none in 2.14.1), Tensor Data Mover on gfx1250, ROCm 10.0 wheels built on AMD's TheRock packages, SYCL free-function kernels and cross-process events on Intel, and `torch.compile` on Python 3.15.

## Checking the Apple Silicon numbers on an M1 Max

The MPS section is the only one with figures, and this machine has an Apple GPU, so these I could test. I took the exact shape and dtype from each PR's own table, ran both official wheels in separate processes, and alternated 2.14.1 and 2.15.0 for ten rounds each. Every process warmed up, then took 15 samples of 100 back-to-back calls followed by one `torch.mps.synchronize()`, so a sample measures throughput rather than one launch plus one sync. The full `norm` took 10 calls per sample, since on 2.14.1 each one took about 40 ms. I report the median of the ten per-process medians and the spread between the fastest and slowest process. The slow ops got fewer calls: upsample backward ten samples of two calls, and QR five single calls per process, in ten processes on 2.15.0 and three on 2.14.1, where one call takes 21 seconds.

One caveat on conditions: other jobs were rendering video on this GPU during parts of the run, and `ioreg`, sampled before each process, often showed the GPU near 100% busy. Spread captures some of that. It was large for the sub-30 µs `F.linear` calls on 2.14.1 (one process ran nearly 3x slower than the rest) and small everywhere else.

| Op, PR shape | 2.14.1 | 2.15.0 | my speedup | PR or blog |
|---|---|---|---|---|
| softmax 1x128256 fp32 | 101.5 µs | 29.0 µs | 3.5x | 8.0x |
| `F.linear` 896 → 128, bf16 + bias | 22.3 µs | 11.7 µs | 1.9x | 5.05x |
| `F.linear` 896 → 896, bf16 + bias | 24.7 µs | 13.0 µs | 1.9x | 3.13x |
| `vector_norm` 4096x4096 bf16 | 39,542 µs | 92.3 µs | 428x | 170x |
| upsample backward, bilinear, to 640x640 | 112.4 ms | 19.25 ms | 5.8x | 21.7x |
| `linalg.qr` 512x512 fp32 | 21,024 ms | 4.99 ms | about 4,200x | about 4,700x |

Every claim holds in direction, and the pattern in the gaps is consistent. Where the old path was a bad algorithm, the speedup survives or grows on older hardware: a full `norm` that took 39.5 ms now takes 92 µs, and QR on the GPU went from about 21 seconds to about 5 ms, which on this Mac is roughly the speed of the CPU path (4.8 to 6.6 ms). Two exploratory QR runs I did earlier, while the GPU was busy with other work, gave 0.7 to 5 seconds per call on 2.15.0; the ten clean processes ranged from 4.5 to 5.7 ms, so treat the QR figure as what an unloaded GPU does. Where the old path was a fine algorithm with high launch overhead, the gain shrinks: softmax and the small decode projections gain 2x to 3.5x here against 3x to 8x in the PRs. The `F.linear` PR reports its 1.23x as a geometric mean over 96 bf16 shapes; on the one 4096-wide shape I added, the gain was 1.1x with overlapping spreads, which is no gain I would claim. If you serve small models on an older Mac, expect the decode-loop gains to be modest and the linear-algebra ones to be large.

## A `torch.compile` comparison I could not run

The first version of this piece timed `torch.compile` on a shared cloud VM and got medians that moved threefold between runs, which settles nothing. I wrote a better design for this Mac: per-wheel Inductor cache directories, the cold run reported separately, then ten warm processes per wheel, alternated, each recording Dynamo's frame counters to prove compilation happened. It never got as far as a timing. Both wheels died with a segmentation fault before printing any result, and one 2.15.0 attempt hung instead; I did not diagnose why, so I make no claim about either release from it. What would settle the question is that script on an idle Linux machine with a pinned clock, ten processes per wheel, with the spread reported. The release notes' compiler items, cached fusion search and lower per-call overhead in compiled code, are what it would test.

## What I would do with this release

If you run NCCL jobs, upgrade, but read your memory budget first. Count the groups your stack creates and multiply by roughly 200 MiB; if that number matters, set `lazy_init` on the groups you create speculatively rather than reaching for `nccl-legacy`, which has one release left. Use `nccl-lazy` for pipeline stages. Pass `device_id` to `init_process_group` instead of relying on `set_device`. Run one job with `TORCH_DIST_USE_NCCL2=0` and one without, and diff the startup logs, since failures that used to appear at the first collective now appear at group creation.

Treat reconfigure as something to try, not something to build on yet. Every function in it has a leading underscore, and the fast path is opt-in for a reason: its correctness depends on rank order. Reconfigure itself is not new: my run worked the same on 2.14.1, and the rewrite already had a full re-init path. What 2.15 adds is the shrink/grow fast path, reconfigure on ROCm, and the default backend that carries it, which puts surviving a dead GPU without a restart within reach of stock PyTorch rather than a separate library.

Upgrade checkpoint readers before writers, set `reduce_dtype` explicitly in FSDP2, and if you are on a Mac, update: the MPS gains are real, and on an M1 Max some of them are larger than PyTorch claims. For profiling the CUDA side once you have a GPU, my [torch.profiler walkthrough](/articles/torch-profiler) is the place to start; for how PyTorch now targets a very different accelerator, see [TorchTPU](/articles/torchtpu).

## Machine, wheels and scripts

Everything I ran used `torch==2.14.1` and `torch==2.15.0` from PyPI in two separate virtual environments, CPython 3.12.3, on an Apple M1 Max with 64 GB under macOS 26.6.2. No third-party code ran. The reconfigure run used gloo over loopback with four spawned processes and a TCP store. Source reading used the `v2.15.0` tag of pytorch/pytorch (commit `31a77fc9`) and the installed wheels' own Python files. Figures for NCCL memory, the TorchTitan matrix, the PR tables and every Blackwell, ROCm and Intel item are the authors' numbers, not mine.
