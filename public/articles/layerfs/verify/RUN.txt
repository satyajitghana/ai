LayerFS verification run, 2026-10-31. Everything below ran on a shared 4-vCPU Linux VM, no root, no FUSE, no Docker, no network except crates.io.

Code:      github.com/Ephemeral-AI-Lab/layerfs commit 35d36575c1eb4d23d4b54534a7030d855db890e7 (the article first read caebd26)
Toolchain: rustc 1.97.0, cargo 1.97.0; SQLite 3.45.1 (python) to read the store afterwards; bundled SQLite in the Rust build
Input:     this site's repository, rev-list --reverse 616e70dc (the 728th commit, 2026-10-27), 157 commits sampled with
           revs[round(i*(728-1)/(157-1))], public/ excluded. Identical to the toy: 569,351 file occurrences, 7,795,062,839 logical bytes,
           4,525 distinct blobs, 132,433,378 bytes (re-derived with git ls-tree before the run).

1. Unit tests of the core crates that define the frozen profile (release deps, test profile opt-level 1):
     cargo test -p layerfs-content --test zero_cdc --test filesystem_limits --test filesystem_profile --test object_identity
   -> 21 passed, 0 failed (tests_content.log). Wall time 8m45 of which nearly all was compiling.

2. The real store, in process (no mount): lfsverify_main.rs, a small crate whose only dependencies are path dependencies on the
   LayerFS workspace (lfsverify_Cargo.toml). It follows the product's own test fixture (engine/crates/layerfs-api/tests/support):
     - snapshot 0 is written to a directory and imported with layerfs_project::init into a fresh SQLite Store, StoragePolicy::frozen_default(),
       Disposable profile; the Store is sealed and installed, then opened by layerfs_store_service::StoreService;
     - snapshots 1..156 are applied as layerfs_api::call("fs.apply") on a fork of main (rm, mkdir, write per changed path, one Commit
       each, via a private Workspace), i.e. the product's commit path with the FUSE layer left out;
     - at the end every file of the last snapshot is read back with fs.read.
   Command:  nice -n 15 lfsverify 157 /home/user/ai 616e70dc <workdir>      (about 70 s)
   Output:   real_store_157.json (per-snapshot newStored and file size), run157.stderr.log, store_breakdown.json (read from the finished
             store.sqlite with python's sqlite3: store_totals, store_policy, object_location by role, pack by domain, dbstat).
   Note: the Store runs SQLite in WAL mode and its main file lags the WAL until it is closed. The per-snapshot file_bytes column in
   real_store_157.json therefore understates; the final size after close is 27,607,040 bytes (store_breakdown.json "page").

3. The edit experiment on the real store: lfsverify_edits.rs -> edits.jsonl. Base file written, then an edited copy written to the same
   path on a fork; newStored is the Commit's own counter. Later cases reuse earlier bases (so their base_new_stored is a few hundred bytes).

4. The toy re-run with the real policy: toy_store_v.py is toy_store.py with three arguments added (END rev, chunk cutoff in bytes,
   zlib|zstd). zstandard 0.25.0 level 3 in a uv venv. Results in toy_variants.json.

Not run: the engine crates that mount (layerfs-fuse, layerfs-daemon, layerfs-sandbox; they need /dev/fuse and root), the dsh-dedup
benchmark (private input, Docker, Btrfs loop devices), fio, merge and .lww tests, Windows/WSL paths.
